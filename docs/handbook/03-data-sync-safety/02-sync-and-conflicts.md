# 同步与冲突处理

NanoFlow 的同步模型适合“一个人，多设备”。它不是多人实时协作系统。理解这一点，可以避免把同步状态误解成聊天软件那种实时协同。

## 同步会做什么

云同步主要做：

- 把本地变更推送到 Supabase；
- 从云端增量拉取其他设备的变更；
- 处理软删除和 tombstone；
- 失败时进入 RetryQueue；
- 在本地和远端版本不一致时按策略处理。

任务同步行必须带有字符串正文。缺少 content 的远端行会被拒绝并保留错误证据，不会被当成空正文继续物化。

正常情况下，增量拉取应该依赖 `updated_at > last_sync_time` 这类条件，而不是每次全量加载所有数据。

每次同步写入还会携带一个稳定的 `operationId`。如果云端已经提交写入，但响应在弱网中丢失，后续重放会沿用同一个 ID，服务端返回第一次操作的结果，而不是再次写入。应用升级可能改变协议版本、部署版本或来源信息，这些审计字段的变化不会把同一笔业务写误判成另一笔写。对于已经带有稳定重放摘要的新记录，如果同一个 `operationId` 携带了不同的任务、项目或删除内容，服务端会明确拒绝它，不会静默覆盖。

连接重试在进入 ActionQueue 重放隔离前，仍沿用同一笔操作的普通重试回调；一旦已经进入 ActionQueue 重放，就会通过带 owner 和 `operationId` 栅栏的持久化 RetryQueue 路径提交。两条路径都保留待同步状态和可追溯的失败信息，用户不需要手动重复保存。

稳定摘要上线前的旧操作记录没有足够证据区分“只有协议或部署信息变化”和“业务内容也变化”。这类记录只会在同一用户范围内返回第一次保存的结果，绝不会再次执行写入；只有旧版完整摘要也精确一致时，服务端才会惰性补齐稳定摘要。完整摘要不一致时仍返回旧结果且不升级摘要，因此不能把这类旧记录描述为已经严格判断了业务内容是否漂移。

同一个 `operationId` 的首次并发请求会在数据库事务内串行解析，避免两个请求同时认为“尚未执行”后重复进入写入。对于已经保存结果的历史任务删除，即使旧批次超过当前客户端的 100 条上限，也会先返回原结果；新的批量删除仍必须遵守当前的输入形状和数量限制。

## LWW 是什么意思

LWW 是 Last-Write-Wins，意思是“最后写入者获胜”。简单理解：

- 同一个任务在设备 A 和设备 B 都被修改；
- 两边后来都同步到云端；
- 系统根据更新时间判断哪一边更新；
- 更新的一边可能覆盖旧的一边。

这不是智能文本合并。它不会自动把两个设备对同一段正文的不同修改拼起来。

## 自动解决冲突还是手动处理

系统设置中的“自动解决冲突”决定冲突被发现后优先走哪条入口。它默认开启，默认策略是 LWW；关闭后，冲突不会被忽略，也不会让同步停止，而是被保留到系统仪表盘和冲突中心，等待你选择本地、云端、合并或系统建议。

| 模式 | 发生冲突时的预期 | 适合什么情况 | 主要风险 |
| --- | --- | --- | --- |
| 自动解决，默认开启 | 系统按 LWW 自动处理可直接收敛的冲突 | 一个用户、设备切换有序、修改较小且已有备份 | 你可能只在稍后发现较早的正文、关系或字段已被较新版本覆盖 |
| 手动处理，关闭自动解决 | 冲突进入仪表盘，需要你在冲突中心选择可信来源或逐项处理 | 导入/恢复后、多设备都离线编辑过、关键正文/附件/关系被修改 | 冲突会积压，继续编辑同一项目会让判断范围变大 |

这个开关是当前账号在当前浏览器中的本地偏好：切换账号后会读取各自的设置，但它目前不会自动同步到其他设备。若你要在多台设备上执行“先人工判断再继续”的流程，应分别在每台设备关闭它；反过来，恢复自动模式也要在每台设备明确设置，不能假定一端的开关已经传播。

### 选择策略前的安全顺序

1. 有重要改动时，先导出当前项目 JSON；有附件时同时导出 ZIP。
2. 导入、恢复或长时间离线编辑后，先关闭自动解决，再让同步把冲突暴露到仪表盘。
3. 在冲突卡片里比对项目、任务数量、正文、关系、附件和最近修改时间。
4. 对能证明一端完整可信的项目，选择本地或云端；两边都有效时选择合并并逐项验证。
5. 所有关键项目完成核对后，再决定是否重新开启自动解决。

切换开关不会删除已有冲突记录、不会倒回已完成的同步，也不会自动恢复被覆盖的内容。已经出现在冲突中心的项目应按 [同步诊断与冲突中心](05-sync-diagnostics-and-conflict-center.md#怎样在冲突中心做选择) 的流程处理，而不是期待切换开关后自行消失。

### 恢复期间正在解决的冲突

如果恢复流程已经进入写入静默，而一个冲突解决操作已经开始，系统会保留这次 writer 的 owner 和会话凭证，让它在等待本地快照或云端 durable settlement 后继续完成发布。恢复不会把这次已经授权的操作误判成普通新写入。

静默期间其他没有同一 continuation 的项目写入会在真正改动状态前被拒绝，保持零写入；切换账号或会话失效时，冲突结果也不会发布到新 owner。这样可以避免恢复中的项目状态被无关写入穿插。

## 多设备编辑的安全方式

建议：

1. 同一时间只在一台设备上编辑同一个项目。
2. 换设备前，先等待当前设备同步稳定。
3. 如果设备 A 离线编辑了很多内容，不要立刻在设备 B 修改同一批任务。
4. 冲突风险高时，先导出 JSON。
5. 重要正文修改前，可以先复制一份到任务内容或外部文档里。

高风险做法：

- 两台设备都离线修改同一个任务正文；
- 在待同步状态下清浏览器数据；
- 导入旧 JSON 后立刻让另一台设备继续同步；
- 手动改数据库行但不理解 `updated_at`。

## 看到 stale 数据时怎么排查

如果你觉得“另一台设备改了，但这里没看到”，按顺序检查：

1. 当前设备是否在线。
2. 当前账户是不是同一个用户。
3. 修改发生的设备是否已经完成同步。
4. 当前设备是否有 pending 或 retry 状态。
5. Supabase RLS 是否把数据过滤掉了。
6. 相关记录的 `updated_at` 是否真的更新。
7. 本地是否被旧缓存或离线状态挡住。

不要第一反应就清浏览器数据。清之前先导出。

当你需要看待同步操作、失败队列、重新同步按钮或本地/云端冲突选择时，继续读 [同步诊断与冲突中心](05-sync-diagnostics-and-conflict-center.md)。

## 用户可以安全采取的动作

| 情况 | 建议动作 |
| --- | --- |
| 只是同步慢 | 等待网络稳定，刷新同步状态 |
| 一台设备有最新数据 | 先在这台设备导出 JSON |
| 两台设备内容不一致 | 选定一台作为当前可信来源 |
| 正在导入、恢复或修复重要项目 | 暂时关闭自动解决，先在冲突中心人工审阅 |
| 怀疑云端权限问题 | 检查登录和 Supabase RLS |
| 大量内容要修复 | 先备份，再按一台设备一个方向恢复 |
