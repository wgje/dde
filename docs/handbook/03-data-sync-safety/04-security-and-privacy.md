# 安全与隐私

NanoFlow 面向个人使用，但它仍然会处理任务内容、附件、语音、外部链接、本地路径和可能的知识库锚点。个人项目也需要清晰的安全边界。

## 哪些密钥不能进前端

前端可以配置：

- Supabase URL；
- Supabase anon key；
- 明确设计为公开的前端开关。

前端绝对不应该配置：

- Supabase service role key；
- Groq API Key；
- FCM private key；
- Sentry auth token；
- 任何第三方服务的服务端密钥。

这些密钥应放在 Supabase Secrets 或部署平台的服务端 Secret 里。

对普通使用者而言，这些变量不需要也不应该手工填写。看到要求你把 service role、第三方 API key 或 FCM 私钥粘进浏览器设置、任务正文或公开仓库时，应当停止操作并联系实例维护者。`anon key` 是浏览器可以使用的公开项目标识；它不是 service role，也不能替代服务端权限策略。

## 数据隔离靠什么

云端数据隔离主要靠 RLS 和 user scope。部署前请确认：

1. 用户数据表已经启用 RLS。
2. policy 使用 `user_id` 或等价身份字段隔离数据。
3. Storage bucket 是私有的。
4. RPC 或 Edge Function 没有绕过用户隔离。
5. 如果多个账号会使用同一实例，用两个账号测试能否互相看到数据。

不要通过“隐藏 UI 按钮”来当安全策略。安全必须在服务端生效。

## 普通使用者应该怎样保护数据

NanoFlow 的隐私边界从你的使用习惯开始。下面这些动作不需要管理员权限，但能避免大部分可预防的泄露和误恢复：

| 场景 | 安全做法 | 不要做什么 |
| --- | --- | --- |
| 公共电脑、共享浏览器或投屏 | 使用独立浏览器配置文件，离开前退出账户；确认桌面小组件和页面没有显示敏感任务标题 | 把浏览器站点数据、下载目录或本地备份当成无关紧要的缓存 |
| 本地模式 | 把数据视为当前浏览器范围内的私有副本，并规律导出 | 因为没有登录就把真实凭证、敏感文件或唯一副本随意放进浏览器 |
| 跨设备工作 | 先等待同步状态收敛，再在另一台设备打开项目 | 在两台设备离线同时编辑同一条敏感任务，再靠“谁最后保存”处理 |
| 导出数据 | 把 JSON、附件 ZIP 和逃生导出当作含敏感内容的文件，放进可信目录 | 直接发送到群聊、公开 issue、截图或无访问控制的网盘链接 |
| 外部资料 | 确认链接目标、来源和可见范围，再打开或把它作为知识锚点 | 把不可信网页、`file:` 路径或网络共享路径伪装成普通任务链接 |

登录、退出、清除浏览器数据和更换账号都可能改变本机可见的工作区。准备做这些动作前，先按 [备份与恢复](03-backup-and-restore.md) 留一个可用副本；不要把“我记得已经同步过”当作恢复证据。

## 部署者应该怎样验证实例边界

私有部署者要同时验证浏览器、数据库、Storage 和 Edge Function 四层。任一层只靠前端隐藏或环境变量命名，都不能替代真正的访问控制。

| 边界 | 应该验证什么 | 最小验收方式 |
| --- | --- | --- |
| 浏览器配置 | 只有 URL、anon key 和明确公开的功能开关进入前端构建 | 运行 `npm run audit:secrets`，并检查部署平台的前端环境变量 |
| 数据库 | 用户、项目和行级资源按当前身份隔离 | 用两个真实测试账号互相尝试读取项目和任务，确认 RLS 拒绝越权访问 |
| Storage | `attachments` bucket 保持私有，路径和 owner 一致 | 用无权账号尝试直接读取另一个账号的对象，确认不会返回文件 |
| Edge Functions | 需要服务端密钥的操作走认证过的函数路径，并验证输入/权限 | 检查函数 Secrets、认证失败响应和日志，确认响应不会回显密钥 |
| 退出与本地状态 | 退出不会让下一个账号继承前一个账号的本地数据 | 在同一浏览器用两个测试账号登录、退出和切换，确认项目和待同步状态正确隔离 |

每次新增数据库表、Storage 路径或 Edge Function 时，都要在同一变更里补上 RLS/授权决策，而不是等 UI 完成后再补安全策略。

## Markdown 和链接安全

任务正文支持 Markdown 和链接，因此必须注意：

- 渲染用户内容时要消毒，防止 XSS。
- 本地路径和 `file:` 链接应走受控处理。
- 网络共享路径和可执行文件不应被误触直接启动。
- 外部链接应该保持清晰，不要伪装成内部任务链接。

如果你只是普通使用者，最重要的是：不要在任务正文里粘贴不可信 HTML，也不要随便打开陌生路径。

Markdown 的可读性不是信任背书。一个看起来像项目链接的文本可以指向外部网站、网络共享或本地路径；点击前先确认目标。需要保存密码、恢复码、私钥或其他长期凭证时，使用专用密码管理器或组织批准的密钥系统，而不是任务正文、Black Box 或附件名称。

## 附件上传安全

日常上传、失败恢复、附件 ZIP 与删除步骤见 [附件与文件安全](../02-use-nanoflow/10-attachments-and-file-safety.md)。本节只说明安全与权限边界。

附件属于高风险输入。完整路径应包含：

- 私有 bucket；
- 用户鉴权；
- 文件类型检查；
- 大小和超时限制；
- 病毒扫描或隔离策略；
- 上传失败后的明确提示。

不要为了“方便预览”把附件 bucket 改成公开。

用户看到“文件已选中”或“上传已开始”不等于文件已经可供其他设备下载。选择、类型校验、上传、扫描、元数据保存和跨设备同步是不同阶段。上传过程中出现错误时，保留原文件和任务上下文，先看 [附件与文件安全](../02-use-nanoflow/10-attachments-and-file-safety.md) 的具体恢复路径，不要为了绕过错误去公开 bucket 或直接暴露对象 URL。

## 附件扫描、隔离与重新扫描

上传成功不一定等于附件已经可以立刻在所有设备使用。启用病毒扫描后，附件可能经历“上传、等待扫描、可用或被隔离”的过程：

1. 上传后先看界面的附件状态，不要只凭文件选择成功就认为流程完成。
2. 如果附件被标记为待处理、隔离或扫描失败，先保留任务和文件信息，不要反复重新上传同一个文件。
3. 修正文件类型、内容或部署配置后，可以走项目提供的重新扫描路径；重新扫描前确认当前账户仍有访问该附件的权限。
4. 扫描结果异常时，部署者应查看 Edge Function 和 Storage 日志，普通使用者应保留原文件副本并联系实例维护者。
5. 不要因为扫描出错就把私有 bucket 改公开，或绕过服务端校验直接把附件当作可信文件使用。

当前扫描策略有几个需要特别保守对待的边界：

- 上传扫描的超时或失败默认会拒绝，而不是悄悄放行；
- 需要扫描的文件有明确大小上限，当前配置是 `10 MB`；能在文件选择器中看到不代表服务端一定接受；
- 下载时会检查扫描状态。未扫描或扫描状态过期时，当前配置默认阻止下载；
- 检测到恶意内容时，策略是隔离并显示安全警告，不应把文件当作普通附件继续传播；
- 扫描状态过期不等于文件已变安全或已变恶意，只表示不能再把旧结果当作最新保证。

这些策略是在保护附件下载者，不是替代杀毒软件、访问控制或你的来源判断。对未知来源的可执行文件、脚本、宏文档或 SVG，保持最小信任：不要下载到生产设备、不要打开、不要为了“恢复工作”跳过安全提示。

## 哪些数据只应留在本机

这些数据通常不应该进入 Supabase：

- 思源本机 token；
- 本地 Relay 配置；
- 桌面备份目录句柄；
- 浏览器本地缓存预览；
- 尚未同步的离线语音原始缓存；
- 只对当前设备有意义的临时状态。

同步越多不一定越安全。该本地隔离的凭证就应该留在本地。

## 导出、备份和共享时的隐私边界

备份提高可恢复性，也会集中保存任务正文、项目结构、链接和可能的附件。因此导出文件的安全等级至少应和原始项目相同。

| 文件或副本 | 可能包含什么 | 建议处理 |
| --- | --- | --- |
| 项目 JSON | 项目、任务正文、标签、计划字段、外部链接和部分状态 | 存放在个人受控目录；恢复后确认是否还需要保留额外副本 |
| 附件 ZIP | 真实附件原件，可能比任务正文更敏感 | 不公开分享；传递前确认接收者、加密方式和保留期 |
| 本地/增强备份 | 浏览器或设备相关的项目副本 | 只放在可信的备份目录或受控同步盘，不要放进公共仓库 |
| 逃生导出或同步诊断包 | 队列、待同步/死信、冲突和恢复上下文 | 仅在需要排障时提供给受信任维护者，先检查是否含敏感标题或内容 |

把备份发给维护者前，先说明项目范围、账号、发生时间和异常提示；不要把不相关的全量导出作为默认附件。维护者也不应该要求用户在公开聊天中粘贴完整的备份或 token。

## 出现安全异常时先做什么

下面的顺序以减少进一步暴露为目标：

1. **暂停扩大影响的操作**：不要继续上传、公开链接、切换账号或删除当前证据。
2. **保留可恢复副本**：数据异常时先导出；恶意文件警告时保留任务引用和提示，不要反复下载或重新上传。
3. **判断边界**：是普通同步异常、文件扫描问题、意外看到别人的数据，还是疑似服务端密钥泄露。
4. **按角色处理**：普通用户联系实例维护者；部署者检查 RLS、Storage policy、Edge Function Secret 和部署日志。
5. **恢复后复核**：确认正确账号、正确项目、附件访问和同步状态都回到预期，再继续工作。

如果怀疑浏览器、公开仓库、日志或聊天记录里出现了服务端密钥，不要只删除那一行文本。将其按已暴露凭证处理：停止使用、在密钥所属平台轮换，并检查是否有未授权访问痕迹。

## 部署前检查表

上线前检查：

1. 前端没有服务端密钥。
2. Supabase RLS 已启用。
3. Storage bucket 是私有的。
4. Edge Function Secret 已配置在服务端。
5. Markdown 渲染没有绕过消毒逻辑。
6. 附件上传有限制和失败提示。
7. 附件 bucket 私有、下载前扫描状态检查和隔离路径已用测试账号验证。
8. 至少做过一次备份和恢复演练。
