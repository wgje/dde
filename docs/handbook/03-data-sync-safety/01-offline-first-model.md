# 离线优先模型

NanoFlow 的核心体验是：你点击、编辑、移动任务时，界面应该立刻反应，而不是等云端请求完成。这就是离线优先的基本含义。

离线优先不等于“任何时候都已经同步完成”。它把一项工作拆成可独立判断的阶段：先让当前设备可靠保住你的操作，再在后台把它带到云端和其他设备。理解这几个阶段，可以避免在最不安全的时候清浏览器数据、换账号或在第二台设备重做同一项工作。

## 读路径是什么

普通读取路径可以理解成：

```text
IndexedDB / 本地缓存 -> 应用状态 -> 界面显示 -> 后台增量拉取云端变更
```

也就是说，应用启动或切换项目时，优先让你看到本地已有状态。云端数据会在后台补充或修正，但不应该让所有日常操作都卡在“等待服务器”上。

你在冷启动、离线、网络很慢或刚从后台回到前台时，可能先看到一份本地快照，再看到后台合并后的状态。这不自动代表数据被覆盖；通常只是读路径先恢复可用界面，再拉取更新。只有当页面提示冲突、待确认或同步错误时，才需要停止并主动判断可信来源。

这带来的好处：

- 没网时仍能看和改；
- 网络慢时界面不至于一直阻塞；
- 手机端体验更稳定；
- 本地备份和恢复更有意义。

## 写路径是什么

普通写入路径可以理解成：

```text
你执行操作 -> 本地状态立即更新 -> UI 立即变化 -> 约 3 秒防抖 -> 推送云端 -> 失败则进入重试
```

因此，一个任务标题刚改完时，至少有两种状态：

1. **本地已经变了**：你在界面上能看到新标题。
2. **云端未必已经成功保存**：还要看同步状态、网络和云端结果。

这不是 bug，而是离线优先的设计结果。

“约 3 秒防抖”是后台推送节奏，不是你必须盯着等待的保存按钮。正常编辑时，继续在同一设备完成当前小段工作即可；准备刷新、退出、切账号、清浏览器数据或换设备前，才需要把注意力放到同步状态上。

## 一次修改有哪三层确认

把“保存成功”拆成三层，最能减少误判：

| 层级 | 你能观察到什么 | 它能证明什么 | 它还不能证明什么 |
| --- | --- | --- | --- |
| 界面已更新 | 标题、状态、层级或条目立刻变了 | 当前操作已进入本地工作流 | 浏览器存储和云端都已稳定 |
| 本地已保存 | 刷新后同一浏览器仍能看到变更，且没有本地存储错误 | 当前浏览器的持久化路径已经接住了数据 | 另一台设备已拿到同一份结果 |
| 云端已确认 | `待同步` 收敛、没有同步错误，并在另一台设备刷新后可见 | 当前已知变更已经能够跨设备对齐 | 之后的并发编辑不会再产生冲突 |

大多数日常编辑只需要前两层。只要工作不离开当前浏览器，就不必为每一个字停下来等待云端。涉及跨设备交接、重要删除、导入导出、登录切换或浏览器清理时，至少确认第三层，或者先做一份导出。

## 本地保存和云端暂不可用时会怎样

NanoFlow 会把“本地能否可靠写入”和“云端是否暂时可用”分开处理：

| 情况 | 应用行为 | 你应该怎么理解 |
| --- | --- | --- |
| 本地快照写入失败 | 本次本地变更不会被提交，应用会提示本地保存失败 | 这不是普通待同步；先保护现有数据，再检查浏览器存储或设备空间 |
| 本地保存成功、云端暂时失败 | 本地已提交的快照不会为了云端错误而回滚，后台会继续重试 | 可以继续本地工作，但不要清理浏览器数据 |
| 云端长时间没有确认 | 本地状态仍会保留，并交给后台重试路径继续收敛 | 导出一份 JSON，再检查登录、网络和云端服务 |
| 当前用户已切换 | 属于旧账号的等待结果会停止继续影响新账号状态 | 切换账号后先等待工作区完成恢复 |

这个设计的目的，是避免网络瞬断让你刚刚完成的本地工作立刻消失；但它也意味着“本地已保存”与“所有设备都已经看到”是两个不同的阶段。

本地持久化对项目快照会做完整性检查；如果正常写入和一次重试仍然失败，系统会进入保护和恢复路径，而不是把“界面刚变了”伪装成安全保存。看到本地存储、队列冻结或逃生导出提示时，按 [PWA、离线与错误恢复](../01-get-started/06-pwa-offline-and-error-recovery.md) 先保全数据。

项目离线快照写入 IndexedDB 时，只有数据库 transaction 完成才算提交成功；transaction 中止或报错都不会被当作已保存。数据库打开被其它页面阻塞时会立即进入失败处理，持续无响应超过 5 秒也会停止等待并检查 localStorage 镜像。只要其中一条本地持久化路径成功，快照仍可用于恢复；两条路径都失败时，本次等待式保存会明确失败，不能继续执行依赖该快照的账号切换或清理。

## 为什么 ID 在客户端生成

NanoFlow 的实体 ID 应该由客户端生成，例如使用 `crypto.randomUUID()`。这样做是为了：

- 离线时也能创建任务；
- 不需要等数据库返回 ID；
- 后续同步时不做临时 ID 映射；
- 多设备合并时实体身份更稳定。

不要把任务先创建成临时 ID，再等云端返回正式 ID。那会让离线数据、引用、附件、连接和恢复都变复杂。

## 待同步和重试是什么意思

如果网络断开、权限异常、云端暂时失败，写入不应该直接消失，而是进入等待、重试、隔离或需要人工确认的路径。

你可以这样理解：

| 状态 | 含义 | 你应该怎么做 |
| --- | --- | --- |
| 本地已保存 | 当前浏览器里已经有这个变更 | 可以继续工作 |
| 待同步 | 还没成功推到云端 | 不要清理浏览器数据 |
| 重试中 | 之前推送失败，正在等恢复 | 检查网络和登录状态 |
| 已同步 | 当前已知状态本地和云端一致 | 可以换设备检查 |

内部队列还会区分更细的状态，例如正在同步、计划重试、检测到冲突、认证阻塞、协议阻塞、死信和存储冻结。不是每个内部名称都会直接显示在界面上，但它们对应的用户决策可以这样理解：

| 你看到的迹象 | 系统大致处在什么阶段 | 先做什么 |
| --- | --- | --- |
| `待同步`、黄色状态或离线提示 | 本地已保留，云端还没有确认 | 留在当前设备继续必要工作；不要清站点数据 |
| `正在同步` 或蓝色状态 | 正在把本地修改推送或拉取 | 等当前轮结束，避免为同一件事重复提交 |
| 灰色重试状态 | 上一轮没成功，系统正等待下一次可用机会 | 检查网络和登录，给当前页面一些时间，不要反复刷新 |
| `操作未能同步` 或 `同步失败` 提示 | 重要操作已经进入失败/死信处理，可能还有依赖操作被暂停 | 先导出，再检查登录、网络和冲突中心；不要假定稍后一定自动恢复 |
| `需确认`、冲突提示或红色状态 | 系统不能安全决定保留本地还是云端版本 | 停止多设备并行编辑，按 [同步与冲突处理](02-sync-and-conflicts.md) 选择可信来源 |
| `存储受限`、队列冻结或逃生导出 | 本地队列的持久化本身遇到风险 | 立即保留导出，释放空间后再继续；不要只重试同一操作 |

如果有待同步内容，最危险的动作是清浏览器数据或直接换设备继续编辑。第二危险的是在多台设备上各自重做一遍“看起来没同步”的同一项操作，这会制造重复或冲突，而不是加快同步。

## 多标签页和多设备时应该期待什么

### 同一浏览器开了多个标签页

同步写入有单写者协调机制，避免多个页面同时冲向云端。它的用户含义是：一个标签页正在处理时，另一个标签页的后台推送可能稍后才执行。不要因为状态没有瞬间变化就同时在两个标签页重复点保存、删除或完成。

更稳妥的做法是：把同一项目的编辑集中在一个标签页；另一个标签页只用于查看，或先刷新确认它已经追上。如果其中一个标签页出现错误提示，以出现真实编辑内容的标签页为准，先导出再决定后续操作。

### 同一账号使用多台设备

云端刷新以后台合并和轮询为有效路径，实时推送不是所有部署都必然启用。换句话说，另一台设备不会承诺秒级看到你的修改。

跨设备交接建议这样做：

1. 在编辑设备完成当前小段工作，等明显的待同步或错误状态收敛。
2. 在接手设备打开相同项目，等待它完成后台刷新；必要时重新打开对应面板或把应用切回前台。
3. 先核对一个关键任务的标题、正文和状态，再继续大批量修改。
4. 如果两台设备各自都有未确认变更，停止继续编辑并转到 [同步与冲突处理](02-sync-and-conflicts.md)，不要靠刷新覆盖其中一边。

本地模式、离线音频缓存、浏览器提示关闭状态和部分“今天已经处理过”的体验状态本来就属于设备范围。它们不会因为同一账号登录在另一台设备就自动变成相同状态。

## 用户应该怎么看保存状态

建议养成这些习惯：

1. 普通单设备使用时，看到界面变化后继续做当前工作；不要把每一次输入都当作要立即跨设备验收的操作。
2. 准备换设备前，等待同步状态稳定，并在目标设备核对一个关键任务。
3. 网络刚恢复时，不要立刻关闭浏览器，给后台同步一次完成和重试的机会。
4. 批量修改、导入、迁移、清理前，先确认没有明显错误，再导出备份。
5. 长时间待同步时，先检查登录、网络、Supabase 配置和权限；仍未收敛就进入同步诊断，而不是无限重试。

## 遇到异常时的安全恢复顺序

这个顺序适用于“我刚改过，但不确定是否保存/同步了”的情况：

1. **先停下重复操作**：不要连续新建、删除或重新输入同一项内容。
2. **保留当前证据**：不要关掉仍然有最新内容的标签页；记录项目、任务和出现的提示。
3. **判断层级**：是普通离线/待同步、需要登录、冲突待确认，还是本地存储风险。
4. **先导出再处理**：要刷新、切账号、清浏览器、导入旧文件或换设备前，先按 [备份与恢复](03-backup-and-restore.md) 保存可用副本。
5. **按问题类型恢复**：网络与登录问题等待重试；冲突进入冲突中心；存储问题走逃生导出和恢复页。
6. **最后核对结果**：在本机和需要使用的另一台设备各看一次关键任务，而不是只看状态图标。

### 不该用来“修复同步”的动作

- 反复刷新页面，期待待同步自动消失；
- 在另一台设备重新创建同名任务；
- 清除站点数据来让同步“重新开始”；
- 不导出就导入旧备份覆盖当前项目；
- 切换到另一个账号后继续修改旧账号的本地工作区。

这些动作会减少你能用于判断和恢复的证据。同步问题优先是数据保护问题，其次才是界面问题。

## 常见问题

### 界面已经变了，为什么另一台设备还没看到？

界面变化只证明本地工作流已经接到操作。另一台设备还需要云端推送、后台拉取和合并；实时推送也不是所有环境的必然前提。先等当前设备的同步状态收敛，再让目标设备刷新项目或回到前台。

### 待同步是不是表示数据还没保存？

不是。它通常表示本地已保留、云端尚未确认。危险不在于马上没有数据，而在于你在确认前清掉浏览器数据、切换账号或让两台设备各自改同一项工作。

### 我可以在离线时切换到另一台设备继续吗？

不建议。另一台设备无法看到尚未推送的本地修改。要么在原设备继续，要么先导出并使用明确的导入/恢复流程；网络恢复后再完成云端对齐。

### 为什么不建议同时开多个标签页编辑同一个项目？

应用会协调后台写入，但它不能替你判断两个页面的意图是否冲突。集中编辑可以减少重复操作和对“哪个页面最新”的猜测。
