# 备份与恢复

NanoFlow 现在有多条恢复通道，但它们不是同一件事。你需要先分清自己要救的是哪一层数据:

- 项目、任务、连接等结构数据；
- 原始附件文件；
- 当前设备上尚未同步的本机状态，例如待上传附件、待同步队列、失败记录和冲突副本；
- 同一浏览器里的内部回滚层。

选错恢复层，最常见的结果不是“恢复失败”，而是“以为恢复了，其实只恢复了一半”。

## 先选正确的恢复层

| 恢复层 | 当前入口 | 适合解决什么 | 关键边界 |
| --- | --- | --- | --- |
| [回收站/归档恢复](../02-use-nanoflow/09-project-settings-and-recovery.md) | 日常任务恢复入口 | 普通误删、误归档 | 不覆盖浏览器数据清理、跨设备覆盖或附件本体丢失 |
| JSON 导出/导入 | 设置中的“备份与恢复” -> `导出` / `导入` | 项目、任务、连接、结构元数据迁移与恢复 | 不包含原始附件二进制；附件 URL 可能过期 |
| 附件 ZIP 导出/导入 | 设置中的“附件备份（ZIP）” -> `导出 ZIP` / `导入 ZIP` | 原始附件文件备份与回填 | 不会重建任务结构；必须依附当前项目/任务匹配 |
| 本地增强备份 | 设置中的“本地增强备份” -> `立即执行备份` / `从备份恢复` | 桌面端灾难恢复，尤其是浏览器数据、待同步状态和待上传附件 | 依赖桌面浏览器与目录权限；恢复按当前账号做 owner 校验 |
| 应用内 IndexedDB 回滚备份 | 无独立用户入口 | 同一浏览器 profile 内的内部回滚保护 | 代码中保留 7 天，不是跨设备、重装或清浏览器数据后的主恢复手段 |

> 关键原则: JSON 和附件 ZIP 是两条独立链路。本地增强备份是第三条链路，它写出的也是 JSON 文件，但内容比普通 JSON 导出更多。

## 什么时候必须先做一份新备份

以下场景开始前，先做一份新的备份，不要直接操作:

- 批量删除、批量移动、重排项目结构；
- 清理浏览器数据、换电脑、重装系统；
- 手动导入旧 JSON 或旧附件 ZIP；
- 开始本地增强备份恢复；
- 处理同步异常、冲突副本、失败记录；
- 怀疑当前设备还有未上传附件或未同步队列；
- 准备修改 Supabase、迁移数据或手动修库。

如果当前设备还能打开 NanoFlow，最低限度先做两件事:

1. 立刻导出一份当前现状 JSON。
2. 如果重要任务带附件，再导出一份对应的附件 ZIP。

如果你正在桌面端并且“本地增强备份”可用，最好再执行一次`立即执行备份`，把本机待同步状态一并保留下来。

## JSON 导出和导入当前到底包含什么

设置页当前会显示一行`备份与恢复`，副标题是`JSON 格式数据`，右侧有`导出`和`导入`两个按钮。

### JSON 导出包含什么

当前导出的 JSON 会写入:

- 项目、任务、连接；
- 任务附件的元数据，例如 `id`、`name`、`size`、`mimeType`、`url`；
- 导出元数据，包括导出时间、格式版本、项目数、任务数、连接数、附件数和校验和。

当前导出**不会**写入原始附件二进制文件。代码里明确把附件放成元数据对象，且 `url` 字段只是附件 URL，并注明“Signed URL 可能过期”。

这意味着:

- JSON 适合恢复结构；
- JSON 不足以单独恢复原始文件；
- 只看到 `attachmentCount` 不代表文件本体已安全备份。

### JSON 导入会做哪些检查

当前导入器在真正导入前会做四类预检:

1. 文件预检: 只接受 `.json` 或 `application/json` / `text/plain`，大小上限 50 MB。
2. JSON 解析: 解析失败会直接报 `JSON 解析失败`。
3. 结构验证: 缺元数据、缺项目、缺版本或项目缺 `id/name` 都会失败。
4. 版本验证: 当前支持版本区间是 `1.0` 到 `2.1`。

如果文件其实是本地增强备份生成的 `BackupData`，当前导入器会先把它转换成普通 `ExportData` 再继续校验。也就是说，本地增强备份文件的项目结构部分和普通 JSON 导入走的是同一套基础导入器。

### JSON 导入时你会看到什么

当前导入预览会额外给出两类提醒:

- 校验和不匹配: 说明文件可能被改过；
- 文件里带附件元数据: 会提示附件 URL 可能过期，导入后可能需要重新上传附件。

手动 JSON 导入遇到冲突项目时，当前界面会弹出确认框:

- 点`确定`: 跳过冲突项目；
- 点`取消`: 覆盖现有项目。

这和“从本地增强备份恢复”的行为不同。后者使用的是`merge`策略，而不是这里的“跳过/覆盖”二选一。

## 附件 ZIP 的边界和安全限制

设置页当前会单独显示一行`附件备份（ZIP）`，右侧有`导出 ZIP`和`导入 ZIP`。空闲时状态文案是`ZIP 原文件导出与分批导入`；导出或导入中会显示百分比和已处理数量。

### 附件 ZIP 到底保存什么

当前 ZIP 备份会写:

- `manifest.json`；
- `attachments/...` 下的附件文件内容；
- 每个附件在 manifest 中的 `taskIds`、`projectIds`、`bundlePath`、`downloadStatus` 等信息。

这条链路的目标是“保住原始文件本体”，不是重建项目结构。

### 导入 ZIP 的当前匹配规则

当前 ZIP 导入优先按 `manifest.json` 恢复:

- 只处理 `taskIds` 不为空、且 `downloadStatus === success` 的条目；
- 只导入当前项目/任务能匹配到的附件；
- 未匹配到项目的附件会被跳过，并记录 `部分附件未匹配到项目，已跳过` 的警告。

如果 manifest 解析失败，导入器会退回到基于 `taskAttachmentMap` 的路径猜测，但本质上仍然要求“当前任务存在、路径能对上”。所以 ZIP 不是独立恢复包，仍然依赖先把任务结构恢复回来。

### ZIP 导入的安全边界

当前 ZIP 解析器有明确限制:

- 最多 500 个 ZIP 条目；
- 每个条目解压后不得超过单附件大小上限，当前是 10 MB；
- 整个 ZIP 解压后的总大小不得超过 100 MB；
- 路径必须是安全相对路径，包含绝对路径、空段、`.`、`..` 或空字符的条目会被跳过。

导入完成后，界面会弹出结果摘要:

- 全成功: `附件导入完成！ 成功: X 跳过: Y`
- 部分失败: `附件导入部分失败。 成功: X 失败: Y 跳过: Z`

这就是你恢复后要核对的第一层证据。

## 本地增强备份（灾难备份 JSON）

当前桌面恢复主路径不是另一个 ZIP，而是一份更完整的 JSON。它由 `DisasterBackupService` 生成，再由 `LocalBackupService` 写到你选定的目录中。

### 什么时候会显示这个区域

设置页只有在 `localBackupService.isAvailable()` 为真时才显示`本地增强备份`区域。当前兼容性判断是:

- 移动设备: 不支持；
- 没有 `showDirectoryPicker` 的浏览器: 不支持，当前提示文案是“请使用 Chrome 浏览器”；
- 桌面且支持 File System Access API: 才显示该区域。

如果你的设置页里根本没有`本地增强备份`，不要假定它在后台已经运行。

### 你会看到哪些可见状态

| 状态 | 当前界面文案/动作 | 代表什么 |
| --- | --- | --- |
| 未授权目录 | `开启本地自动备份`、`选择目录` | 还没有可用目录句柄，无法写文件 |
| 已授权目录 | 目录名、`✓ 已授权`、自动备份开关、`立即执行备份`、`从备份恢复` | 当前设备已经可以写入与读取备份 |
| 目录已保存但未授权 | 目录名、`需要恢复权限`、`恢复` | 句柄还在，但本轮浏览器会话需要重新授权 |
| 手动备份成功 | 弹窗显示 `备份成功！`、文件名和位置 | 当前目录里已经落盘一份新备份 |
| 手动备份延后 | 弹窗显示 `备份暂未完成` | 当前没有写出半成品，稍后重试更安全 |

### 文件名、保留策略和写入校验

当前本地增强备份文件名格式是:

`nanoflow-backup-YYYY-MM-DD_HH-mm-ss.json`

当前实现还会做三件事:

1. 写入后立刻反读校验文件大小；
2. 成功后自动清理旧文件；
3. 最多保留 30 份备份文件。

恢复面板里当前只显示最新的 10 个文件，但目录中可能还有更多历史文件。

### 这份 JSON 比普通导出多了什么

当前本地增强备份在普通项目结构之外，还会打包三类数据:

1. 项目结构数据:
   - projects
   - tasks
   - connections
2. 云端用户状态:
   - user_preferences
   - focus_sessions
   - transcription_usage
   - routine_tasks
   - routine_completions
3. 本机 localState:
   - offline snapshot
   - dock/launch snapshot
   - parked task cache
   - retry queue
   - action queue
   - dead letters
   - conflicts
   - external pending links
   - attachment upload outbox
   - data safety snapshot

其中`attachmentUploadOutbox`会把待上传附件的二进制内容编码成 `base64` 写进 JSON，目的就是避免“只留下附件元数据，却丢掉真正还没传到云端的文件本体”。

### 它什么时候不会写出文件

本地增强备份不会在“云端用户状态读取已被延后”的情况下写出文件。

当前实现的行为是:

- 先构建完整 payload；
- 如果浏览器正处在网络恢复窗口，或读取云端状态时命中“浏览器恢复连接中”的延后条件；
- 则返回 `deferred: true`，并提示 `浏览器恢复连接中，自动备份稍后重试`；
- 当前轮不会把一份缺云端用户状态的半成品写进目录。

这条边界很重要: 看到“备份暂未完成”时，别把它当作已成功备份。

### 多设备边界

当前实现只会把以下设置同步到云端偏好:

- 是否开启自动备份；
- 自动备份间隔。

**不会**同步以下内容:

- 目录路径；
- DirectoryHandle 本身；
- 任何其他设备上的目录授权状态。

因此每台设备都要各自完成一次目录选择或权限恢复。不要因为另一台设备已经在备份，就假定当前设备也能自动写到同一个目录。

## 恢复前检查清单

开始任何恢复动作前，先按这个清单做:

1. 选定一台设备作为这次恢复的唯一操作端，其他设备先停止编辑。
2. 导出一份当前现状 JSON；有重要附件时再导出一份当前附件 ZIP。
3. 如果你要用本地增强备份恢复，先确认当前账号正确。
4. 如果本地增强备份区域显示`需要恢复权限`，先点`恢复`，不要换一个未知目录继续。
5. 先决定你要恢复的是:
   - 只有结构 -> JSON；
   - 结构 + 原始附件 -> JSON + ZIP；
   - 结构 + 本机待同步状态 -> 本地增强备份。
6. 记录恢复前的异常表现，例如少了哪些项目、哪些附件打不开、是否有冲突中心或失败记录。

## 恢复路线 A：先恢复 JSON，再恢复附件 ZIP

这是跨设备、跨平台最稳妥的人工恢复路径。

### 什么时候用这条路

- 你有可信 JSON；
- 你还保留着对应的附件 ZIP；
- 你主要关心项目结构和文件，而不是当前设备的待同步队列；
- 当前设备没有“本地增强备份”入口，或者你不打算恢复本机 localState。

### 操作顺序

1. 在当前设备导出一份“出问题后的现状” JSON。
2. 打开设置中的`导入`，选择可信 JSON。
3. 看完预览中的警告和冲突数量再决定下一步。
4. 如果是手动 JSON 导入:
   - `确定` = 跳过冲突项目；
   - `取消` = 覆盖现有项目。
5. JSON 导入完成后，先检查项目名称、任务数量、关键连接。
6. 再用`导入 ZIP`导入同一份备份对应的附件包。
7. 导入 ZIP 后，立即核对成功/失败/跳过数量，并抽查关键附件能否打开。

### 这条路不会帮你恢复什么

这条路不会自动恢复:

- 待上传附件 outbox；
- Action Queue；
- Retry Queue；
- dead letters；
- conflict copies；
- 离线快照和 launch/dock snapshot。

如果这些内容对你重要，改走[恢复路线 B](#恢复路线-b从本地增强备份恢复)。

## 恢复路线 B：从本地增强备份恢复

这条路是当前最接近“整机级恢复”的用户可操作路径。

### 当前恢复流程会显示什么

点击`从备份恢复`后，当前界面会经历这些状态:

- `loading`: `读取备份文件...`
- `list`: 显示目录中的备份文件列表
- `preview`: 显示即将恢复的项目/任务/连接，以及可恢复的本机待同步状态
- `restoring`: `恢复中，请勿关闭...`
- `done`: 成功摘要
- `error`: 错误摘要

### 操作顺序

1. 打开设置中的`本地增强备份`。
2. 如果看到`需要恢复权限`，先点`恢复`。
3. 点击`从备份恢复`。
4. 在文件列表中选择正确时间点的备份。
5. 点击`选择此备份`进入预览。
6. 预览页先看三组数量:
   - 项目
   - 任务
   - 连接
7. 如果页面出现`本机待恢复状态`，再看这些数量是否符合预期:
   - 附件上传
   - 待同步
   - 待重试
   - 失败记录
   - 冲突副本
8. 看清当前警告: `⚠️ 以合并方式导入，不会删除现有数据`
9. 确认后点击`确认恢复`，等待完成，不要关闭页面。

### 当前恢复策略的真实边界

当前“从本地增强备份恢复”不是强制覆盖，而是两段式恢复:

1. 项目结构部分走导入器，并使用 `merge` 冲突策略；
2. 成功后再把待上传附件、Action Queue、Retry Queue、dead letters 和 conflicts 分别恢复回对应存储。

对同 ID 的现有项目，当前 `merge` 行为是:

- 不直接删除现有项目；
- 不盲目整体覆盖；
- 主要把缺失的任务和连接补进去。

所以这条路更像“把可信本地备份并入当前工作区，再补回本机待同步状态”，而不是“把当前一切全部抹掉重来”。

### 当前账号不对时会发生什么

当前恢复流程会做 owner 校验。

如果备份里的 `ownerUserId` 与当前账号不一致，恢复会直接被阻止，并给出明确错误:

`该本地备份属于其他账号，已阻止恢复以避免把待同步队列、失败记录或冲突副本写入当前账号。请切换到对应账号后再恢复。`

看到这条提示时，不要换策略硬导入，也不要在当前账号下继续试第二份同源备份。先切到对应账号。

### 恢复过程中切账号或切上下文会怎样

当前恢复流程会持续检查“当前账号 + 当前恢复上下文”是否还和开始时一致。

如果恢复过程中账号变了，或恢复上下文被打断，流程会停止并报:

`恢复已停止：当前账号或恢复上下文已变化，请重新选择备份。`

这不是异常边角，而是当前设计的安全阀。看到这条消息时，应从选择备份那一步重新开始。

### 成功后你会看到什么

当前成功提示至少会包含:

- `恢复成功！已导入 X 个项目`

如果还恢复了本机待同步状态，提示会继续追加:

- `已恢复 X 个待上传附件`
- `已恢复 X 个待同步操作`
- `已恢复 X 个待重试同步操作`
- `已恢复 X 条同步失败记录`
- `已恢复 X 条冲突副本`

这不是装饰性文案，而是你恢复后第一轮验收的依据。

## 云端恢复和本地恢复怎么选

当前代码把“云端用户状态”和“本机 localState”明确分开处理，所以你可以按下面的原则选:

| 你的问题 | 优先路线 | 原因 |
| --- | --- | --- |
| 只是结构错了、项目少了、想迁移到新设备 | JSON 导出/导入 | 最便携，跨平台 |
| 结构恢复后还要把原始附件一并带回来 | JSON + 附件 ZIP | JSON 不含原始文件 |
| 浏览器数据损坏，且你担心丢了待同步操作、待上传附件、失败记录或冲突副本 | 本地增强备份 | 只有这条路会恢复 localState |
| 只剩云端侧已同步数据，没有本地增强备份目录 | 先做云端侧处置，再回到 JSON/ZIP 或本地增强备份入口对齐客户端 | 当前用户界面明确暴露的是 JSON、附件 ZIP 和本地增强备份三条入口 |

实操上可以记一句话:

- **已同步到云端的数据**，可以指望云端侧存在；
- **还停留在当前设备本地的待同步状态**，不要指望云端恢复自动把它们带回来。

## 恢复后必须验证什么

不要把“导入成功”当作恢复完成。恢复后至少做下面这轮检查。

### 结构检查

- 项目数量是否对；
- 关键项目名称是否都在；
- 顶层任务和关键分支是否都在；
- 关键连接是否完整；
- 如果你依赖 Parking / 本机上下文，回到关键任务确认它们没有继续丢。

### 附件检查

- ZIP 导入结果里的`失败`和`跳过`是否符合预期；
- 至少抽查 2 到 3 个关键附件能否打开；
- 如果导入预览曾提示“附件 URL 可能已过期”，恢复后就按“需要重新上传”的标准去核查，不要假定旧 URL 一定还有效。

### 本机待同步状态检查

如果本地增强备份预览或成功提示里出现过这些计数，就逐项对照:

- 待上传附件数量；
- 待同步操作数量；
- 待重试数量；
- 失败记录数量；
- 冲突副本数量。

必要时继续看[同步诊断与冲突中心](05-sync-diagnostics-and-conflict-center.md)确认同步是否重新排空。

### 多设备检查

- 在这台设备完成检查前，其他设备不要继续编辑；
- 当前设备确认恢复正确后，再让同步追平；
- 同步稳定前，不要在第二台设备导入另一份旧备份。

## 恢复时不要做什么

- 不要在还没导出现状前就清浏览器数据。
- 不要把普通 JSON 当作“已经包含附件本体”的完整备份。
- 不要先导入 ZIP，再指望它把任务结构补出来。
- 不要在错误账号下恢复本地增强备份。
- 不要看到`备份暂未完成`就当作已经成功写出文件。
- 不要在`恢复中，请勿关闭...`时关闭页面或切账号。
- 不要两台设备同时恢复两份不同备份。
- 不要把应用内部 IndexedDB 回滚层当作跨设备灾难恢复方案。
