# 开发与维护

这一部分面向贡献者、维护者和协助维护项目的 AI。它不教你“从哪个文件开始随手改”，而是帮助你在改动前先确认所有权、风险、验证范围和文档责任。NanoFlow 的本地优先状态、同步契约、移动端体验、数据库策略和部署产物互相影响，改动只在一个界面上看起来正常并不足以说明它是安全的。

## 这部分适合谁

当你准备做下面任一件事时，从这里开始：

- 首次在本机启动 NanoFlow，或需要分清本地离线开发和云端联调；
- 修改文本视图、Flow、Focus、Parking Dock、同步、备份、附件或 Android 小组件；
- 修改 Supabase 迁移、RLS、Storage、Edge Function、环境变量或发布流程；
- 接手一个陌生模块，想知道状态、服务、测试和文档各由谁负责；
- 新增、调整或核对面向真人的手册，以及给 AI 检索用的 Context7 契约；
- 排查一次异步活动、计时器、订阅、队列或恢复流程为什么会重复、漏跑或无法停止。

如果你只是要日常使用应用，应回到 [NanoFlow 使用手册首页](../index.md)。这里的命令、目录和验证门禁是给改变项目的人准备的，不是普通用户的操作步骤。

## 按改动类型选择路径

| 你准备改变什么 | 先读 | 再确认 | 最小验证起点 |
| --- | --- | --- | --- |
| 开发机、依赖、启动地址或环境变量 | [开发环境](01-development-environment.md) | 当前工作目录、Node.js 版本、环境校验结果 | `npm start`、`npm run validate-env` |
| 不了解某项功能由哪些模块共同实现 | [仓库地图](02-repository-map.md) | 功能目录、状态/服务边界、相邻测试 | 该功能的相关规格测试 |
| 文本、Flow、Focus 或 Parking Dock 的可见行为 | [仓库地图](02-repository-map.md) | 对应功能目录和业务服务 | 相关规格测试；必要时组件或服务测试分组 |
| 本地保存、同步、登录、附件或跨设备行为 | [仓库地图](02-repository-map.md) | `src/app/core/state/`、同步服务、模型和云端契约 | 定向同步/服务测试，加上适用的契约门禁 |
| 数据库、RLS、Storage 或 Edge Function | [Supabase 运维](../04-deploy-operate/02-supabase-operations.md) | 迁移、函数、生成类型和部署环境 | 迁移审查、生成类型、相关契约与运行验证 |
| 性能、启动、Flow 按需加载或发布产物 | [测试与质量](03-testing-and-quality.md) | 受影响的入口和性能预算 | `npm run perf:guard` |
| 读者可见的流程、恢复操作或运维步骤 | [文档维护](04-documentation-maintenance.md) | 对应手册页和 `change-coverage.json` 路由 | `npm run docs:human:guard` |
| 定时器、订阅、后台队列或重试/恢复链 | [运行时入口与活动审计](05-runtime-entry-activity-audit.md) | 启动入口、释放逻辑、失败后的状态 | 定向规格测试与活动审计清单 |

表中的“起点”不是上限。它只告诉你应该先用哪条能直接反驳错误实现的证据；一旦改动跨过同步、数据库、性能、部署或共享状态边界，就按 [测试与质量](03-testing-and-quality.md) 扩大验证。

## 推荐的维护顺序

1. **先写清要证明的事实。** 例如“任务标题离线后仍可恢复”“该迁移不会绕过 RLS”“附件失败后仍能保留恢复证据”，而不是只写“修复同步”。
2. **先定位所有权，再读局部实现。** 按仓库指令从 CodeGraph 上下文开始；在 NanoFlow 中优先使用上下文包和语义查询。CodeGraph 不可用时，先走仓库规定的 NanoFlow 适配器回退，不要直接以文件名猜测或用大范围文本搜索替代结构事实。
3. **确认输入、状态和输出。** 找到用户入口、持久化/网络边界、失败分支和已有测试。一个按钮常常只是一条业务链的入口，并不拥有状态或同步写入。
4. **做最小且可验证的改动。** 复用现有 store、服务和模型；不要为了方便再建一层并行状态或绕过现有服务直接写云端。
5. **先跑最窄的证明。** 让最能覆盖本次断言的规格、脚本或复现先失败后通过；再补充共享契约、质量或性能门禁。
6. **同步文档。** 读者可观察到的行为要更新中文手册，源码所有权、数据模型、API 或检索契约要更新 Context7。覆盖映射必须能把实现路径指向真正解释该流程的手册页。
7. **记录事实而不是印象。** 交付说明要写清实际运行的命令、退出结果、仍然失败的已知项及其是否与当前改动无关。

## 每次改动都要守住的边界

### 本地状态与同步不是同一件事

界面刷新、本地持久化和云端确认是不同阶段。UI 组件不应把“画面已经更新”当作“远端已经写入”，也不应绕过同步服务直接发起临时 Supabase 写入。涉及这条边界时，同时看本地状态、持久化、同步队列和错误恢复路径。

### 功能目录不等于唯一所有者

`src/app/features/` 负责功能界面和交互，但任务操作、模型、全局状态和同步往往位于其他目录。修改 Flow、Focus、Parking Dock 或文本视图时，要沿着入口继续看到业务服务和测试，而不是只改组件模板或样式。

### 后端规则必须和前端契约一起改

迁移、RLS、Storage 策略和 Edge Function 在 `supabase/`，生成的数据库类型在 `src/types/`。改变 schema 或服务端输入输出时，既要验证安全和部署路径，也要更新前端使用方、生成类型以及相应的运维/Context7 文档。

### 文档是交付物的一部分

手册首页、目录清单、专题文章和 `change-coverage.json` 构成给真人的阅读路径；`docs/context7/` 记录给维护者和检索工具使用的源码事实。不要用根目录概览页来敷衍一个具体的用户流程，也不要把源代码注释当作已经完成了读者文档。

## 交付前留下什么证据

一次可追溯的改动至少应留下下面的信息：

- 变更的实际行为或不变量，以及它对谁可见；
- 涉及的所有权路径和为什么没有绕过现有边界；
- 已运行的定向验证命令和结果；
- 是否运行了文档、耦合、性能、迁移或构建门禁，以及原因；
- 当前工作树若仍有失败，失败文件和它与本次改动的关系；
- 更新了哪些中文手册与 Context7 页面，或为什么这次没有读者可见或源码契约变化。

这比“已经测试过”更有用：下一位维护者能复现你的判断，也能区分新问题和旧工作树残留。

## 常见误区

| 误区 | 为什么不可靠 | 更好的做法 |
| --- | --- | --- |
| 只按目录名改一个组件 | 状态、服务和同步可能在别处拥有真正写入权 | 先用仓库地图确认完整业务链和相邻测试 |
| 全量测试绿了就忽略定向测试 | 宽泛命令不一定覆盖你声称修复的分支 | 先运行能直接证明断言的最小规格 |
| 只更新 Context7 或只更新中文手册 | 两者的受众、内容和可验证方式不同 | 根据读者流程和源码契约分别更新，必要时两边都改 |
| 为了让门禁通过而改一个无关的概览页 | 读者仍无法找到新行为的正确说明 | 更新覆盖映射指向的专题页，或创建真正独立的新文章 |
| 把脏工作树里的所有失败都归到当前改动 | 这样会掩盖基线问题和真实回归 | 用失败路径、定向验证和当前 diff 区分来源 |

## 下一步

1. 从 [仓库地图](02-repository-map.md) 找到本次改动的主所有者和高风险边界。
2. 用 [测试与质量](03-testing-and-quality.md) 选出第一条验证命令。
3. 行为或契约有变化时，按 [文档维护](04-documentation-maintenance.md) 同步文档与覆盖映射。
