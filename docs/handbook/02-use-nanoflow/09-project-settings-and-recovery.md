# 项目、设置与回收站

项目决定任务、流程图、Parking Dock 和搜索结果属于哪一组工作。设置决定应用如何显示、如何导入导出和是否启用本地增强备份；回收站与归档则是日常误操作的第一层恢复入口。

这几个入口都很重要，但不应该混在一次高风险操作里。创建或切换项目时先确认上下文；导入、恢复、批量删除前先备份；回收站只处理普通误删，不是替代长期备份的保险箱。

## 先理解项目和当前上下文

NanoFlow 的操作大多以当前项目为范围：文本任务树、Flow 节点、停泊任务、回收站中的任务和搜索后的预览都要先落在正确项目里。开始任何批量操作前，先确认侧边栏或当前工作区显示的是你要处理的项目。

下面几种情况最容易在错误的上下文里操作：

- 刚从搜索结果跳到另一个项目；
- 处理多个相似名称的项目；
- 在手机上切换项目后立即打开编辑器；
- 在一个设备恢复任务，同时另一台设备仍停留在旧项目；
- 导入 JSON 后，新旧项目名称看起来相近。

安全做法是：先看项目名，再看任务标题和层级，最后才执行恢复、删除、导入或拖拽。若搜索结果来自其他项目，先让项目切换稳定；已停泊任务会进入该项目的 Parking Dock 预览，而不是被自动恢复。详情见 [文本视图](01-text-view.md)。

## 创建和切换项目

### 创建项目

新建项目时，项目名称是必填项，描述是可选项。名称适合写“这组工作最终要达成什么”，描述适合写范围、约束或项目边界。

推荐步骤：

1. 创建前先确认这不是现有项目中的一个阶段或子任务。
2. 用结果命名，例如 `2026 年个人报税准备`、`家庭网络改造`，不要只写“杂项”或“新项目”。
3. 在描述中写一两句边界，例如“只处理宽带迁移和路由器配置，不包含全屋布线”。
4. 创建后立刻添加一个结果导向的顶层任务，再补充可以推进的子任务。
5. 如果项目包含真实数据，先做一次 JSON 导出，作为后续大规模整理的起点。

项目名称不能完全为空。输入被拒绝时，先检查是否只输入了空格；不要反复点击创建按钮。

### 切换项目

切换项目后，先做一项低风险确认，例如查看任务树顶层标题或搜索一个确定存在的任务。确认当前项目无误后再进行以下操作：

- 编辑任务正文或计划字段；
- 恢复或永久删除任务；
- 调整流程图关系；
- 导入数据；
- 打开 Parking Dock 或 Focus。

不要把“搜索到了任务”理解成“当前项目已经正确切换”。跨项目跳转是一个过程，连续选择多个结果时以最后一次选择为准。

## 设置中哪些操作影响数据

“系统设置”集中放置了外观、数据传输、本地备份、专注偏好和外部知识源等控制。它们的风险并不相同。

| 设置区域 | 主要作用 | 会不会直接改变任务数据 | 使用建议 |
| --- | --- | --- |
| 主题和颜色模式 | 改变浅色、深色或跟随系统的显示方式 | 不会 | 可以随时调整；它只影响外观 |
| JSON 导出和导入 | 导出或导入项目、任务和结构数据 | 导入会改变本机工作区 | 导入前先导出现状，导入后检查项目和任务数量 |
| 附件 ZIP 导出和导入 | 单独备份或恢复附件文件本体 | 导入会写入附件 | 先导入 JSON，再导入对应 ZIP |
| 本地增强备份 | 选择目录、定时备份、从备份恢复 | 恢复会写入项目数据 | 只在确认目录权限和备份来源后使用 |
| 自动解决冲突 | 选择默认 LWW 自动处理，或把冲突留给仪表盘人工选择 | 会改变发生冲突时的处理入口，不会停止同步 | 高风险多设备编辑前先确定策略；它按当前账号和浏览器本地保存 |
| Focus、Gate、Black Box、思源等偏好 | 改变对应功能的行为或入口 | 取决于具体功能 | 进入对应功能的专门手册后再调，不要在不理解作用时批量切换 |

主题和颜色模式不影响数据；导入、恢复和清空回收站则是数据操作。不要因为它们都位于设置或弹窗中，就把它们当作同等风险的按钮。

主题和颜色模式在当前浏览器会立即生效。已登录并配置云同步时，NanoFlow 会把这两个值作为用户偏好异步加入持久化队列；网络暂不可用或短暂失败时，当前设备仍保留刚选的外观，并保存待处理的偏好记录，等后续条件恢复后再尝试同步。未登录或本地模式下，它们只属于当前浏览器资料。

因此，不要把主题已切换当成另一台设备已经更新的证据。需要多设备保持一致时，在一台设备上完成一次调整，等待同步状态恢复正常，再在另一台设备打开设置确认；不要两端同时反复切换相反的主题或颜色模式。

“自动解决冲突”默认开启，使用 LWW 作为自动方向；关闭后，发现的冲突会进入系统仪表盘由你人工判断。这个选择当前按登录账号隔离地保存在本机浏览器，不会自动替其他设备切换相同策略。完整的取舍与恢复顺序见 [同步与冲突处理](../03-data-sync-safety/02-sync-and-conflicts.md#自动解决冲突还是手动处理)。

## 日常节律与 Focus 偏好

设置里的“日常节律”和 Focus 相关开关会立即影响当前设备的工作方式，并在已登录时异步写入偏好同步。它们不是项目数据迁移、回收站或自动修复工具；把同一项设置在多台设备同时来回切换，仍可能按较新的偏好更新时间覆盖较早选择。

| 设置 | 它改变什么 | 不会做什么 |
| --- | --- | --- |
| 日常任务槽 | 在 Parking Dock 的空档中提供可重复的小行动，并记录当天已完成次数 | 不会自动把普通项目任务改成例行任务 |
| 重置时间 | 决定“当天”的逻辑边界，例如凌晨前后的完成次数算到哪一天 | 不会回写或删除历史任务 |
| Gate、Black Box、Strata 开关 | 决定对应的专注入口、快速收集或已完成项展示是否启用 | 开关本身不会删除已有 Black Box 记录、任务或停泊条目 |
| 高/低负荷休息提醒 | 调整累计不同负荷专注多久后给轻提醒的阈值 | 不是日历提醒、闹钟或跨设备强制通知 |

建议一次只调整一个习惯相关设置，然后实际进入 Focus 或 Parking Dock 验证。离线时设置会先保存在当前浏览器；恢复同步后再在另一台设备确认，避免两端同时把同一偏好改成相反值。

日常任务槽的创建、完成上限和逻辑日切见 [Parking Dock 停泊坞](03-parking-dock.md#日常任务槽和逻辑日切)。Gate、Black Box、Strata 和休息提醒如何影响专注工作见 [Focus 专注模式](04-focus-mode.md#设置如何改变-focus)。

## 登录后迁移本地数据

如果你先在未登录或本地模式下创建项目，之后再登录，NanoFlow 可能会显示“发现本地数据”窗口。它展示本地项目、云端项目、仅本地项目和可能重叠的项目数量，并要求你决定登录前的数据应如何进入后续工作区。

这不是普通的“同步失败”提示，也不是可以随意跳过的欢迎页。它处理的是两个可能都包含真实工作的来源：当前浏览器中的访客数据，以及登录账户下的云端数据。看见它时，先停止在另一台设备继续编辑同一个项目；在有条件时，先按本页的 JSON 导出步骤保留一份当前状态。

### 先看清来源，再选择策略

窗口中的四种选择对应不同的保留范围。不要只根据按钮颜色或“看起来安全”来决定。

| 界面选择 | 实际处理方向 | 适合什么情况 | 选择前必须确认 |
| --- | --- | --- | --- |
| 上传本地数据 | 将本地项目逐个上传到当前登录账户 | 本地是主要工作来源，云端没有同一批关键项目 | 云端账户正确；本地项目和附件的备份已准备好 |
| 智能合并 | 合并本地和云端的项目内容 | 两边都分别做过工作，且愿意逐项核对合并结果 | 能接受同一任务可能按较新的更新时间取值；合并后有时间检查关键项目 |
| 使用云端数据 | 不上传访客数据，清除本地访客数据标记并以云端为准 | 云端是可信且完整的工作来源，本地只是试用或旧副本 | 本地没有未备份的重要内容 |
| 丢弃本地数据 | 清除访客数据，并清掉离线快照、重试队列和待同步计数 | 本地数据确定无价值，需要从干净的云端状态开始 | 已导出或明确放弃本地工作；这是四项里最彻底的本地清理 |

“上传本地数据”和“智能合并”都会先做数据完整性检查，并尝试创建一次迁移快照。严重完整性问题会阻止迁移；快照保存失败时，应用会提示你先手动导出。这个快照是恢复辅助，不是独立备份，不能替代 JSON 和附件 ZIP。

上传或合并过程中，某个项目失败时，本地数据会保留，界面会将本次迁移视为失败，而不是悄悄删除原始内容。上传或合并成功后，应用仍会核对云端结果；出现“部分数据可能未完全同步”之类的提示时，先检查项目列表和关键任务，不要立刻开始下一轮批量编辑。

### 用一个决策顺序避免误删

1. 先写下或截图窗口中的本地、云端和可能冲突数量。
2. 本地包含唯一工作时，先导出 JSON；包含附件时也导出 ZIP。
3. 云端完全可信且本地只是旧副本，才考虑“使用云端数据”。
4. 两边都有新增工作时，优先“智能合并”，然后立即检查顶层任务、最近编辑的正文、Flow 连接和附件入口。
5. 只有在本地数据确认无价值时才用“丢弃本地数据”。不要把它当作解决网络错误或登录失败的快捷按钮。
6. 迁移完成后，先在当前设备确认状态稳定，再让其他设备恢复编辑。

同一任务同时存在于本地和云端时，智能合并会保留双方各自新增的任务和连接；双方都有的任务会按较新的更新时间取值。这降低了遗漏新增内容的风险，但不等于系统理解了文字语义。对重要正文、计划字段和附件，仍应由你做最终核对。

## 遇到迁移失败或中断时怎么办

迁移过程中不要关闭页面、切换账户、清浏览器数据，也不要在另一台设备开始导入旧备份。窗口会在处理期间阻止关闭，目的是避免同时发出两次选择；网络、登录状态或完整性检查失败时，则应主动停下来，而不是换一个更激进的策略重试。

推荐处理顺序：

1. 记录错误提示、所选策略和窗口中的项目数量。
2. 检查网络连接和当前登录账户是否正确；需要重新登录时，完成登录后再回到迁移流程。
3. 如果应用仍可操作，先导出当前 JSON；附件重要时一并导出 ZIP。
4. 对上传或合并的部分失败，先核对本地项目仍在，再修复网络或账户问题后使用同一种策略重试。不要改选“使用云端数据”或“丢弃本地数据”来强行结束提示。
5. 如果完整性检查失败，先保留原始导出和错误信息；不要手工删除看起来“异常”的任务来碰运气。
6. 迁移完成后若发现数量或关键内容不对，停止后续编辑，按 [同步与冲突处理](../03-data-sync-safety/02-sync-and-conflicts.md) 和 [备份与恢复](../03-data-sync-safety/03-backup-and-restore.md) 的顺序处理。

访客数据接近过期时，应用会提醒你尽快登录迁移或手动导出。把这类提示当作备份提醒，而不是自动清理前的倒计时游戏：有价值的数据应在过期提示出现前就完成迁移或导出。

## JSON、附件 ZIP 和本地增强备份

### JSON 导出和导入

JSON 用于保存项目、任务、连接和相关结构信息。导入前，应用会校验文件并生成预览；遇到已存在的数据时，需要按照界面提示选择冲突处理方式。

导入的安全顺序：

1. 在当前设备先导出一份现状 JSON。
2. 确认你要导入的是可信文件，不要把来源不明的 JSON 当作恢复文件。
3. 导入后先检查项目名称、任务数量、顶层任务和关键关系。
4. 不要立刻在另一台设备继续编辑，先让当前设备的保存和同步稳定。
5. 确认结构正确后，再处理附件或继续整理。

JSON 不包含原始附件二进制文件。完整的恢复原则见 [备份与恢复](../03-data-sync-safety/03-backup-and-restore.md)。

### 附件 ZIP 导出和导入

附件 ZIP 与 JSON 是两套独立传输。附件导入会尝试按任务和项目匹配内容；未匹配到当前项目任务的附件会被跳过并给出提示。

因此应当：

1. 先导入包含任务结构的 JSON。
2. 再导入与该 JSON 对应的附件 ZIP。
3. 查看导入结果中的成功、失败和跳过数量。
4. 对跳过或失败的附件，不要立刻重复导入；先确认任务是否存在于当前项目、文件是否属于同一份备份。

只导出 JSON 不等于附件已经备份；只导入 ZIP 也不会重建任务结构。

### 本地增强备份

支持的浏览器会在设置中显示“本地增强备份”。你可以选择一个目录、开启自动备份、执行立即备份，并从已保存的本地备份发起恢复。

推荐做法：

1. 选择可信、可长期访问的目录。
2. 如果需要跨机器保存，选择由 OneDrive、Dropbox、坚果云或其他可信同步工具管理的目录。
3. 开启自动备份后，确认界面显示最近一次备份时间或可用的备份文件。
4. 浏览器提示重新授权目录时，恢复权限后再继续；不要换一个未知目录绕过权限提示。
5. 恢复前先导出现状，并确认选择的是正确的备份时间点。

本地增强备份依赖浏览器能力和目录权限；设置中没有该区域时，不要假定它已在后台运行。它是 JSON/附件备份和云同步的补充，而不是替代品。

## 回收站、归档和永久删除的区别

回收站窗口有“已删除”和“已归档”两类内容。它们看起来相似，但恢复含义不同。

| 状态 | 任务在哪里 | 应该怎样处理 |
| --- | --- | --- |
| 已删除 | 回收站的已删除列表 | 确认误删后使用恢复；必要时再检查原项目 |
| 已归档 | 回收站的已归档列表 | 取消归档后，任务会回到主视图的活动状态 |
| 已停泊 | Parking Dock，而不是回收站 | 按停泊流程恢复或继续等待 |
| 永久删除 | 不再是日常恢复入口可找回的内容 | 只在有可信备份且确认无价值时执行 |

对单个已删除任务，恢复操作会把它恢复为可继续使用的任务。对已归档任务，取消归档会让它重新回到活动主视图。

永久删除和清空回收站都会要求确认。删除父任务时，界面会提示它包含的子任务数量；这类操作前先导出，并确认你理解会影响哪些子任务。自动清理周期也不是备份策略，不要依赖“过一段时间还能找回”作为唯一保护。

## 恢复任务的安全顺序

普通误删时，按照这个顺序操作：

1. 暂停在其他设备继续编辑同一个项目。
2. 导出当前现状，保留误操作后的证据和最新改动。
3. 打开回收站，先确认任务是已删除还是已归档。
4. 只恢复一个最有代表性的任务，不要第一步就批量恢复。
5. 回到正确项目，检查任务标题、父子层级、正文和附件入口。
6. 恢复多条任务前，确认第一条恢复后的状态符合预期。
7. 让当前设备保存和同步稳定后，再在其他设备查看结果。

找不到任务时，先检查项目上下文、回收站的当前标签页和任务标题；不要马上清浏览器数据或启动多台设备的导入。仍无法恢复时，按 [备份与恢复](../03-data-sync-safety/03-backup-and-restore.md) 的完整顺序处理。

## 批量整理前的检查清单

准备删除、归档、导入或恢复很多任务时，先逐项确认：

- 当前项目正确；
- 当前设备不是离线、登录失效或同步错误状态；
- 已导出 JSON；包含附件时也已导出 ZIP；
- 知道任务是应该删除、归档还是停泊；
- 已检查父任务是否包含关键子任务；
- 没有另一台设备正在编辑同一批任务；
- 已了解恢复完成后要如何验证任务树和附件；
- 不会在验证前清空回收站或清浏览器数据。

任何一项无法确认时，先停止批量操作。对个人工作系统来说，少花几分钟验证，通常比从多设备和旧备份里恢复要便宜得多。

## 常见问题

### 我在设置里修改主题，会影响同步或任务吗？

不会。主题和颜色模式只改变显示方式。看到任务变化、同步错误或数据缺失时，应检查同步状态、项目上下文或恢复路径，而不是回退主题设置。

### 为什么附件 ZIP 导入后有一部分被跳过？

附件需要匹配当前项目中的任务。先确认对应 JSON 是否已经成功导入，任务 ID 和项目是否来自同一份备份；不要在任务结构不完整时反复导入 ZIP。

### 回收站和归档到底该选哪个？

不确定以后还要不要看、但暂时不推进的任务，优先考虑 [Parking Dock 停泊坞](03-parking-dock.md)。已完成或长期不活跃、但需要留痕的任务用归档。明确误删才去回收站恢复；确定无价值且已有备份才永久删除。

### 恢复后任务没有立刻出现在眼前，是否应该再次恢复？

先确认当前项目、文本/Flow 视图和搜索条件，再等待保存状态稳定。重复恢复可能制造更难判断的状态。若仍找不到，停止继续操作并按备份恢复流程检查。

### 本地增强备份没有显示或提示需要权限怎么办？

这通常说明当前浏览器不支持对应能力，或之前选择的目录需要重新授权。不要把它当作已经成功运行的备份；改用 JSON 与附件 ZIP 导出，同时选择支持的桌面浏览器或恢复目录权限。
