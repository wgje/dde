# Parking Dock 停泊坞

Parking Dock 用来处理一种很常见的状态：这件事还重要，但现在不该占用当前任务列表。它既不是删除，也不是归档，而是“暂时停一下，之后还要回来”。

## 什么任务应该停泊

适合停泊的任务：

- 等别人回复；
- 等某个日期再处理；
- 当前不做，但怕忘；
- 和当前 Focus 无关，但未来仍重要；
- 暂时缺资料，不能继续推进；
- 今天的注意力范围太满，需要挪开。

不适合停泊的任务：

- 已经没价值的任务，应该删除；
- 已经完成且长期不用看的任务，应该归档；
- 今天马上要做的任务，应该留在当前任务列表或 Focus；
- 没有任何行动价值的想法，应该从 Black Box 里丢弃。

## 从任务到 Dock 控制台

Parking Dock 可以从文本视图、Flow 视图或 Dock 内部把一个已有任务带进当前专注控制台；也可以在 Dock 中快速创建一个临时条目。把已有任务放进 Dock 不等于删除、归档或复制它，它只是让这项工作进入当前的停泊/专注状态机。真正的项目、任务正文和附件仍属于原来的项目上下文。

进入 Dock 前，先确认当前项目正确，再决定每张卡在当前时段扮演什么角色：

- 现在要推进的主任务；
- 可以作为备选的下一步；
- 必须等待外部条件的任务；
- 零碎时间才能处理的轻量动作。

不要把整个项目一次拖进 Dock。Dock 是有限的当前工作控制台，不是第二个永久列表。卡片太多时，先从任务树或 Flow 里选出一到三个真实能推进的候选项；其余继续留在项目、Parking Dock 的等待状态或日常任务槽中。

## 读懂控制台状态

Dock 卡片和状态机把任务状态分成下面几类。状态名称描述的是当前处理阶段，不是对任务价值的评判。

| 状态 | 意味着什么 | 你下一步应做什么 |
| --- | --- | --- |
| 待启动 | 任务已进入 Dock，但还没有成为当前执行项 | 补齐预计时长和负荷，或选择它作为主任务 |
| 专注中 | 当前正在推进的主任务 | 只处理这一个明确步骤；完成、等待或切换前先记录结果 |
| 挂起等待 | 任务正在等外部信息、时间或条件，且已经记录等待时长 | 不要重复编辑同一任务；转去可执行的下一张卡 |
| 等待结束 | 原先的等待窗口已经结束 | 回看卡片和原任务，决定恢复、继续等待还是放弃/归档 |
| 停滞中 | 当前卡没有形成可继续的正常推进路径 | 先补充下一步、等待原因或计划信息，而不是把它标成完成 |
| 已完成 | Dock 已收到完成动作 | 回到原项目确认任务状态、正文和后续任务是否正确 |

等待结束不会自动替你完成任务，也不代表外部条件真的已满足。它只是提醒你重新判断。多个任务同时挂起时，Dock 可能进入碎片阶段并显示日常任务槽；这时优先处理轻量槽或等待最近结束的任务，不要为了退出该状态而随便完成一张卡。

## 等待、切换与完成的安全顺序

### 需要等待时

对“等回复”“等构建”“等约定时间”这类任务，选择等待并设置一个真实可复查的分钟数。Dock 会把等待时长写入任务的计划字段，并将卡片切到“挂起等待”。如果连续挂起多项任务，系统会把注意力切换到碎片阶段，这是提示你此刻没有适合深度推进的工作，不是故障。

等待不是删除、归档或无限期推迟。等待前把原因和回来后的第一步写进任务正文或 Dock 详情；等待结束后先核对条件是否真的满足，再恢复或重新设置等待。

### 要换一项任务时

选择另一张卡会把它设为当前主任务，并把原来的专注任务退回 Dock。它不会自动改变项目优先级，也不会证明原任务已经完成。切换前写下当前进度，尤其是刚读完资料、刚修改正文或刚得到外部答复时。

### 真正完成时

“完成”应只用于已经达到任务结果的工作。点击后先等 Dock 状态稳定，再回到项目检查该任务、其后续子任务和附件入口。不要把“我现在不想做”当成完成；这种情况应选择等待、切换、停泊或归档。

如果卡片点击无响应、状态反复回退或当前设备显示待同步，先停止重复点击，检查同步状态和原任务是否仍存在。不要在两台设备同时完成或切换同一张 Dock 卡。

## 快速调整计划信息

Dock 的快速计划面板用于在不离开当前工作流的情况下调整三类轻量字段：

| 字段 | 用途 | 不是用来做什么 |
| --- | --- | --- |
| 预计投入 | 当前这一步预计要花多久 | 不是截止日期，也不是项目总工期 |
| 认知负荷 | 标记这一步更适合高负荷还是低负荷时段 | 不是优先级、重要性或绩效评级 |
| 等待窗口 | 记录这一步因外部条件需要等待多久 | 不是日历提醒，也不表示任务已经完成 |

对来自项目的任务，这些修改会写回任务的计划字段；对 Dock 内临时创建的条目，会在后续归档到项目时一并带入。等待时长不能超过预计投入：输入或选择不合理组合时，应用会校正为可保存的值并提示你。看到校正提示时，重新判断任务是不是应该拆成更小的下一步，而不是不断放大预计时间。

建议只为当前卡设置能帮助下一次决策的信息。复杂背景、验收条件和外部链接仍应写在任务正文、计划字段或知识锚点中，不要把 Dock 快捷面板当成完整项目文档。

## 就地创建任务与退出 Focus

Dock 中的“快速创建”适合专注过程中突然出现、但不值得立刻离开当前界面的行动。新条目会先创建一条可恢复的 Black Box 记录，再作为 Dock 卡进入当前会话；因此创建失败时不应假定它已经成为项目任务。

在使用就地创建前，先确认当前活动项目正确。应用把这类条目归档到活动项目时，会尝试创建正式任务并带上标题、详情、预计投入、认知负荷和等待窗口；完成状态也会一并处理。没有活动项目，或归档中的任一步失败时，条目会保留失败状态，需要你停止退出流程、检查 Black Box 和当前项目，然后手动把内容保存为正式任务。

安全顺序：

1. 先切到正确项目，再在 Dock 中快速创建。
2. 给临时条目写足以恢复上下文的标题和一句详情。
3. 离开 Focus 后，确认活动项目里出现了对应的正式任务，并核对计划字段。
4. 看见归档失败、缺少项目或同步异常时，不要清 Dock 或 Black Box；先导出或手动创建项目任务。

Focus 场景中的遮罩、雷达和 Zen 画面都是帮助收窄注意力的界面层。关闭遮罩不会完成或移除任务；Zen 全屏停顿时，点击、触摸或按 `Esc` 只会退出该停顿画面，同样不会改变任务状态。若另一窗口正在控制同一 Focus 会话而当前界面变成只读，回到控制窗口操作，避免两个窗口同时修改 Dock。

## 停泊任务时要写清楚什么

停泊不是把任务扔进一个黑洞。停泊时最好补充：

| 信息 | 示例 |
| --- | --- |
| 为什么停泊 | `等张三确认合同版本` |
| 什么时候再看 | `周五下午复查` |
| 回来后第一步做什么 | `打开对方邮件，确认附件是否更新` |
| 当前卡点 | `缺少报价单` |
| 是否重要 | `高优先级，不能超过本周` |

如果界面支持提醒、备注或 pin，就尽量填清楚。未来的你不应该重新猜“当时为什么停泊”。

## 如何恢复停泊任务

当任务重新变得可执行：

1. 打开 Parking Dock。
2. 找到对应任务。
3. 看停泊备注，确认为什么它当时被停泊。
4. 如果已经可以做，恢复到任务列表或送入 Focus。
5. 如果仍然不能做，更新备注或提醒时间。
6. 如果已经没价值，走删除或归档路径。

恢复后建议立刻补充任务正文，写下新的下一步。

## 提醒和停泊通知怎么处理

停泊任务的提醒是为了让你回访，不是让应用反复打断你。收到提醒或停泊通知后，按下面顺序处理：

1. 先看任务标题和停泊备注，确认这是哪个项目、为什么被停泊。
2. 能立刻推进时，恢复任务或送入 Focus，并补写下一步。
3. 现在仍不能推进时，更新提醒时间和阻塞原因，不要只是忽略通知。
4. 确认无价值时，转到归档或删除路径。
5. 同一条提醒已经处理后，如果短时间又看到类似提示，先检查任务是否仍处于停泊和到期状态，再重复操作。

如果提醒在多设备之间看起来不一致，先让当前设备同步稳定，再在另一端确认；不要在两端同时修改同一条停泊备注或提醒时间。

## 日常任务槽和逻辑日切

日常任务槽适合“等待中的停泊任务暂时都不能推进，但你仍有一段零碎时间”的场景。它不是普通项目任务的副本，而是一个可重复的小行动名额，例如“整理 10 分钟桌面资料”或“复查一个等待中的报价”。Parking Dock 进入空档/碎片阶段时，会把仍可完成的日常槽展示出来；你也可以在系统设置中预先维护它们。

### 创建、启用和移除

创建一个日常任务槽时，要填写两件事：

1. 标题：写成可在短时间内完成的动作，不要写“推进项目”或“处理所有消息”。
2. 当日最多次数：范围是 1 到 24，表示这个动作在一个逻辑日里最多可标记完成多少次。

新槽默认启用。临时不想看到某个习惯时，优先关闭它；确定不再需要时才移除。移除会把该例行项的启用状态同步为关闭，不应作为清理某个普通项目任务或历史记录的方式。

完成一个槽会把当天完成次数加一。达到上限后，它在当前逻辑日不再是可继续完成的槽。保存失败时，应用会回退本次槽位改动；看到点击后又恢复原状、或另一端未出现预期状态时，先停止连续点击，确认当前设备的保存和同步状态。

### 什么是“逻辑日”

设置中的“重置时间”按本地小时定义一天从什么时候开始。若重置时间设为 `04:00`，凌晨 `00:00` 到 `03:59` 的完成记录仍属于前一个逻辑日；到达或越过该边界后，槽的当日完成次数会归零。

这个设置适合夜间工作者，但不应频繁改动。改动前先想清楚你希望“熬夜完成的一次复查”算在昨天还是今天；不要用反复改重置时间来绕过每天的完成上限。跨设备工作时，尽量让所有设备同步到同一个偏好后再继续记录。

### 一个安全的使用模式

1. 先只创建一到三个真正轻量的槽，默认每天一次。
2. 在 Parking Dock 出现空档时，选择一个槽完成，而不是临时把大量长期任务塞进 Focus。
3. 到达上限后，回到正常任务或停泊列表判断下一步；不要把同一动作拆成多个名称相近的槽来制造完成感。
4. 登录用户的槽配置和完成记录会进入同步队列。切换设备前等待当前设备状态稳定，并避免两台设备同时完成同一个槽。
5. 例行项如果连续多日不再有价值，关闭或移除它，而不是让它变成新的待办堆积。

## 停泊、归档、删除、Focus 的区别

| 操作 | 意味着什么 | 适合场景 |
| --- | --- | --- |
| 停泊 | 之后还要回来处理 | 等回复、等时间、暂时挪开 |
| 归档 | 长期不活跃，但保留记录 | 完成、过期但要留痕 |
| 删除 | 从当前工作中移除 | 无价值、重复、测试任务 |
| Focus | 当前时段要集中处理 | 今天或此刻真正要推进 |

如果你只是“不想现在看到它”，优先考虑停泊；如果你确定不再需要，才删除或归档。

## 使用建议

- 每天开始工作前看一眼停泊坞，确认有没有到期或高优先级任务。
- 例行槽只服务零碎时间；真正需要推进的工作仍应回到项目任务、Focus 或停泊流程。
- 不要把 Parking Dock 当成永久仓库。
- 停泊任务太多时，说明你需要做一次整理，而不是继续停泊。
- 高风险任务停泊前，先在正文里写清楚当前状态。
- 已经同步到云端的停泊状态，也要注意多设备编辑可能产生覆盖。
