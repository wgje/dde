# 文本视图

文本视图是 NanoFlow 的主工作区。绝大多数日常任务管理都应该在这里完成：创建任务、拆分任务、编辑正文、调整层级、搜索、批量处理、删除和恢复。

## 文本视图适合做什么

优先在文本视图里做这些事：

- 快速新增任务；
- 修改任务标题；
- 给任务写执行说明；
- 把任务拆成子任务；
- 调整任务顺序和父子关系；
- 搜索某个项目或任务；
- 批量删除低价值任务；
- 从回收或归档入口恢复内容。

如果你只是要推进工作，不需要先打开流程图。流程图适合“看关系”，文本视图适合“真正编辑和推进”。

## 创建任务的建议方式

一个清晰任务通常包含三层信息：

1. **标题**：一句话说明要做什么，例如“整理下载目录里的合同文件”。
2. **正文**：写执行步骤、判断标准、链接、注意事项。
3. **位置**：放在正确项目、正确父任务、正确阶段下。

不建议这样写标题：

- `处理一下`
- `资料`
- `待办`
- `看情况`

建议改成：

- `整理下载目录中的合同 PDF`
- `确认 Supabase Storage bucket 权限`
- `把本周复盘草稿补成可发布版本`

标题越清楚，搜索和 Focus 推荐越有用。

## 任务层级怎么组织

层级不是越深越好。推荐结构：

```text
项目目标
  - 阶段或工作包
    - 可以执行的具体任务
      - 必要时再拆的子步骤
```

使用建议：

- 顶层任务写结果，不写零散动作。
- 子任务写动作，尽量能在一个工作时段推进。
- 如果层级超过几层还看不清，说明应该拆项目或重命名中间节点。
- 不要把长篇资料塞成很多层任务；资料适合放在思源或外部文档里。

## 正文、Markdown 和链接

任务正文适合写：

- 清单；
- 执行步骤；
- 外部链接；
- 本地文件路径；
- 关联任务；
- 简短背景；
- 验收标准。

示例：

```markdown
目标：把合同文件按年份归档。

- [ ] 找到下载目录里的合同 PDF
- [ ] 按年份放入对应文件夹
- [ ] 命名成“年份-客户-事项”

参考目录：D:\Documents\Contracts
```

链接处理细节：

| 写法 | 用途 | 注意 |
| --- | --- | --- |
| `https://example.com` | 外部网页 | 会按外链处理 |
| `./docs/guide.md` | 相对文档路径 | 写成真实链接前，先确认目标文件存在 |
| `task:<taskId>` | 关联 NanoFlow 任务 | 适合稳定任务内链 |
| `C:\Users\me\Docs\Plan.md` | Windows 本地路径 | 路径有空格时用 Markdown 链接 |
| `file:` 链接 | 本地文件入口 | 应走受控处理，不直接暴露原始 file URL |

高风险本地路径、网络共享路径和可执行文件不应该被随意直接打开。

任务需要保存真实文件时，使用附件入口，不要把二进制文件路径或大段 Base64 塞进正文。附件上传、扫描、删除与 ZIP 备份有独立的状态和安全边界，读 [附件与文件安全](10-attachments-and-file-safety.md) 后再迁移或批量整理文件。

## 编辑草稿、计划字段与触控拖拽

编辑任务时，先区分“还在编辑的草稿”和“已经提交的任务值”：

1. 输入标题、正文、预计时长、等待时间或认知负荷后，先确认当前编辑框仍显示你想保存的内容。
2. 点击保存、切换任务或结束编辑后，等待界面回到稳定状态，再判断本地保存是否成功。
3. 如果保存提示失败，不要立刻重新输入或刷新页面；先保留当前草稿，确认任务正文是否仍在，再检查同步和本地存储状态。
4. 同一任务在多设备编辑时，先让一个设备完成保存和同步，再在另一台设备继续改。

手机拖拽任务时：

- 长按或移动到触发条件后，界面会进入拖拽状态并给出视觉反馈；
- 拖动过程中如果手势被浏览器、系统电话或页面滚动中断，先松手并等待界面恢复，不要连续重复拖动；
- 拖拽没有落到有效位置时，回到原列表确认任务是否仍在原位置；
- 如果拖拽后任务看起来没有移动，刷新前先观察本地状态和待同步提示，避免把一次延迟渲染误判为数据丢失。

这类操作的安全原则是：先确认本地状态，再判断云端是否已完成同步。

如果恢复流程正在进行，文本视图会继续遵守原 owner 和会话的保存语义。已经带有同一 continuation 的操作可以在恢复诊断确认后继续完成；失效或没有 continuation 的写入会在状态变更前被拒绝。看到恢复中的提示时，先等待恢复诊断和保存状态稳定，不要重复编辑同一任务制造第二次写入。

任务编辑器中的预计时长、等待时间、认知负荷和注意事项用于补充“怎么安排这件事”，不要把它们和标题、正文或 Markdown 待办混在一起。计划字段适合写分钟数和注意力强度；注意事项适合写前提、风险和等待原因。完整规则见 [任务僚机与计划信息](08-task-sidecar-and-planning.md)。

## 搜索和批量操作

搜索适合用来“回到上下文”：

1. 输入关键词。
2. 打开匹配任务；结果来自其他项目时，先确认应用已经切换到该项目。
3. 普通任务会定位到对应 Flow 节点；已经停泊的任务会打开目标项目的 Parking Dock 预览，而不会自动恢复任务。
4. 修改标题、正文、状态或计划信息；停泊任务应先看停泊备注和下一步，再决定恢复、继续停泊或送入 Focus。
5. 清空搜索，再进行拖拽或批量整理。

连续点选多个跨项目搜索结果时，以最后一次选择为准。项目切换尚未稳定时，不要同时拖拽、恢复或删除搜索到的停泊任务；先确认当前项目、Dock 和任务预览已经一致。

批量操作前请先判断风险：

- 只是批量移动低价值测试任务：可以直接做。
- 要删除真实任务：先导出 JSON。
- 要整理包含附件的任务：同时确认附件 ZIP 备份。
- 多设备开启同步时：等当前同步状态稳定后再做大批量操作。

## 移动端使用细节

手机端默认应该使用文本视图，因为它比流程图轻：

- 卡片布局更适合窄屏；
- 长按或触控操作更适合移动端；
- 侧栏通常通过手势打开；
- 流程图按需加载，避免启动慢和内存压力；
- 大量编辑时仍建议回到桌面端操作。

如果你发现手机上操作很慢，先确认是不是长期停留在流程图视图。
