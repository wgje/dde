# 附件与文件安全

附件把任务和真实文件关联起来，但它不是“选中文件就算完成”的轻量功能。当前实现同时涉及本地持久化 outbox、后台重试、私有 Storage、临时签名 URL，以及可选的安全扫描与下载前复查。

本文只写这次源码核对到的真实行为。它会明确区分三类事情：

1. 当前实现已经保证的行为；
2. 当前实现提供了 helper、但我没有确认每个入口都在用的行为；
3. 当前实现没有承诺、你不应依赖的行为。

> [!NOTE]
> 我这次核对到的文本任务编辑器模板里，附件按钮和附件列表片段目前是注释状态，因此本文不按“某个固定按钮一定在这里”来写，而按附件生命周期、安全边界和恢复动作来写。你的实例如果已经暴露附件入口，下面这些边界仍然成立；如果当前界面暂时没有入口，请把本文当成附件链路说明和排障基线。

## 先看结论：你现在能依赖什么

先记住这几条，后面每一节都只是把它们展开：

- **单文件大小上限是 10 MB。** 任务附件数量上限是 20。
- **文件选择成功不等于云端可用。** 当前实现会先写本地 pending 记录，再排队做真正上传。
- **离线或扫描服务暂时不可用时，附件可能先以本地待同步状态存在。** 这时同一浏览器里可以继续保留上下文，但另一台设备还看不到。
- **当前实现确实有附件下载前安全复查 helper，但我没有确认所有预览/下载入口都强制调用它。** 不要把“能点开”当成“已经二次复查通过”。
- **当前实现是软删除优先。** 从任务中删除附件，先写 `deletedAt`；真正的远端文件清理走独立 cleanup 队列，不承诺立刻物理删除。
- **JSON 导出不包含原始附件。** 原始文件要靠附件 ZIP 或实例自己的保留策略恢复。
- **清浏览器站点数据会伤到未完成附件。** pending 上传依赖本机浏览器持久化；换设备、清缓存、切账号前先看同步状态并导出。

## 上传前的选择与校验

### 先确认四件事

上传前先确认：

1. 你在正确的任务和项目里。
2. 你准备保留原文件副本，至少保留到上传、同步和备份都完成。
3. 你知道这份文件适不适合进入任务工作区，而不是把附件当成敏感资料保险箱。
4. 你当前浏览器没有处在“存储空间快满、待同步已堆积、离线又准备清缓存”的危险状态。

如果你只是想记录路径、网页或知识材料，优先放任务正文链接，或改用 [思源知识锚点](06-siyuan-knowledge-anchors.md)。

### 当前实现会拦什么

当前代码里的前置拦截分三层：

| 层级 | 已核对到的行为 | 使用者应该怎么理解 |
| --- | --- | --- |
| 数量与大小 | 文本任务附件控制器会拒绝超过 10 MB 的文件，并限制每个任务最多 20 个附件 | 这是你最先遇到的硬限制 |
| 文件类型 | 文件类型校验默认开启，要求扩展名、MIME、魔数一致；未知类型默认不放行 | “能选中”不等于“能上传” |
| 危险类型 | 明确拒绝可执行文件、脚本、HTML 等高风险类型 | 不要尝试绕过；这不是 UI 建议，而是后端前置拒绝 |

当前白名单覆盖的是常见图片、PDF、Office 文档、纯文本、Markdown、CSV、JSON、XML、YAML 和 ZIP。当前黑名单明确拒绝 `exe`、`msi`、`bat`、`cmd`、`js`、`ps1`、`sh`、`py`、`php`、`html`、`jar` 等执行或脚本类文件。

另外，上传路径里的 `userId / projectId / taskId` 段也会校验，只允许安全字符。如果你看到“用户 ID 包含不安全字符”“项目 ID 包含不安全字符”这类错误，不要继续重试同一操作，先让实例维护者修复数据或路径生成逻辑。

## 真实上传生命周期

下面这张表是这次源码核对到的真实附件生命周期，不是理想化流程：

| 阶段 | 系统真实动作 | 你应该怎么判断 |
| --- | --- | --- |
| 1. 选择文件 | 先做大小、类型、路径安全校验 | 立刻失败时先看错误文字，不要重复选同一个文件 |
| 2. 写本地 pending 记录 | 先把待上传 Blob 和恢复元数据写进本机 outbox；IndexedDB 失败时退回 localStorage 兜底 | 这是“本机已记住待上传文件”，不是“云端已有文件” |
| 3. 任务里出现附件条目 | 当前实现会先生成本地占位附件，URL 形如 `nanoflow-local-attachment://...` | 看到文件名不等于跨设备可访问 |
| 4. 入同步队列 | 把附件 create 操作写入 durable action queue | 这一步失败时，用户看到的通常是“附件上传队列持久化失败” |
| 5. 后台真正上传 | 队列处理器读取本地 Blob，再做一次扫描与远端上传 | 这一步依赖网络、登录、Storage 和扫描服务 |
| 6. 回写任务元数据 | 远端上传成功后，还要把最终附件对象回写到任务并继续同步 | “文件已传上去”与“任务元数据已同步”是两步，不要混为一谈 |
| 7. 清理本地 pending | 只有上传和后续任务更新收敛后，才移除本地 pending 记录 | pending 没清掉时，系统还会继续恢复或重试 |

### 一次上传为什么会分成两步

这是当前实现最重要的安全边界之一：

- 第一步是“本机先记住这份待上传文件”；
- 第二步才是“后台真正把它发到远端，并把任务记录更新到最终状态”。

所以，**任务里出现一个附件名，或同步状态里出现待同步计数，都不能证明另一台设备已经能下载这份文件。**

### 元数据失败时不会把半成品默默留给你

当前实现里，如果远端文件已经上传，但签名 URL 生成失败，系统会：

1. 先把待清理路径写进 cleanup outbox；
2. 立即尝试删掉刚上传的远端对象；
3. 即时清理失败时保留 cleanup 记录，留给后续清理批次。

这意味着当前实现更倾向于“回收无法访问的半成品”，而不是把一个已上传但无法正确引用的文件假装成成功。

## 离线、outbox 与自动重试

### 离线时到底会发生什么

如果当前实例没有可用的 Supabase 连接，或者上传前扫描遇到可恢复错误，附件会转成“本地先保留、远端稍后补传”的模式。当前已核对到的可恢复扫描错误码是：

- `SERVICE_UNAVAILABLE`
- `SCAN_TIMEOUT`
- `NETWORK_ERROR`

这时系统会给附件写入一份本地 `pending` 扫描元数据，并把真正远端上传推迟到后续队列处理，而不是直接把这次操作判成永久失败。

### 哪些本地数据一定要保护

未完成附件依赖本机浏览器持久化：

- 主存储是 IndexedDB；
- IndexedDB 不可写时，当前实现会退回 localStorage；
- 两边的记录都按 `ownerUserId + blobKey + operationId` 做 owner-scoped 存储。

这带来两个结论：

1. **同一浏览器里，网络恢复后有机会继续处理原来的 pending 附件。**
2. **清浏览器站点数据、换无痕窗口、换浏览器、直接换设备，都会让未完成附件变得不可靠。**

### 自动恢复不会跨账号接管

当前实现的 pending 上传记录和 cleanup 记录都按 `ownerUserId` 归属检查。切换到另一个账号时，系统不会把前一个账号的 pending Blob 当成当前账号的待上传文件继续回放。

这对隐私是好事，但也意味着：**你不能指望“换个账号重新进来”帮你恢复未完成附件。**

### 任务已经删了时会怎样

如果后台发现附件原本要写回的任务在本地已经有 tombstone，当前实现不会无限重试，而是：

1. 回收这条 pending 上传；
2. 把可能已经写到远端的对象路径加入 cleanup 队列；
3. 等待远端清理收敛。

所以，删除任务后不要立刻反复上传同名文件来“试试看有没有成功”，先让清理与同步状态稳定。

## 你实际会看到哪些状态

当前实现里，最可靠的用户可见反馈不是“完整附件状态面板”，而是这几类提示：

| 可见位置 | 已核对到的提示 | 代表什么 |
| --- | --- | --- |
| 上传/删除 toast | `附件数量已达上限`、`文件过大`、`上传成功`、`上传失败`、`删除成功` | 当前动作是否被前置拦截、提交成功或失败 |
| 离线横幅 | `离线模式已启用`、`已切换到离线模式`、`云端服务暂时不可用`、`网络已恢复`、`服务已恢复` | 你现在是本地继续工作，还是正在恢复云端 |
| 同步状态条 | `X 待同步`、`连接中断`、`在线`、`本地可用`、`导出待同步数据` | 当前还有多少可见待同步操作，以及是否已进入逃生导出场景 |

### 不要过度依赖的状态

当前源码里确实定义了附件上传状态机：

- `pending`
- `uploading`
- `completed`
- `error`
- `cancelled`

完成或错误项还会在约 3 秒后自动从状态列表移除。

但这次我没有在当前公开附件入口里核对到一个稳定可见、逐项展示这些状态的界面。因此，**在当前版本里，你更应该依赖 toast、离线横幅、同步状态条和任务是否最终收敛，而不是假设自己一定能看见一条长期停留的附件进度条。**

## 扫描、隔离与下载安全边界

### 上传前扫描的真实边界

当前扫描状态模型定义了这些状态：

- `pending`
- `scanning`
- `clean`
- `threat_detected`
- `failed`
- `quarantined`
- `skipped`

但“状态枚举存在”不等于“当前界面一定把每种状态都显式展示出来”。你现在能可靠依赖的是：

- **超出扫描上限的大文件会直接拒绝上传**，并给出“文件过大”的错误；
- **被判定为恶意文件时会直接拒绝上传**，并触发 `安全警告` toast；
- **部分被视为安全的 MIME 类型会走 `skipped`，而不是云端扫描**；
- **网络/服务类可恢复扫描错误会把附件转成本地 pending，而不是直接丢弃。**

### `quarantined` 现在能不能当成用户可操作状态

不能直接这样承诺。

这次核对到的附件上传路径里，恶意文件是在上传前直接拒绝；我没有确认到当前文本任务附件入口会把同一份恶意文件继续保留成一个“用户可见、可手动解封”的隔离附件项。

因此，本文把 `quarantined` 视为**元数据和系统状态能力的一部分**，而不是承诺你今天一定会在附件列表里看到一个固定的“隔离中”按钮或恢复流。

### 下载前复查能不能当成统一保证

也不能。

当前仓库里确实有下载前安全复查 helper：

- 没有 `scanFileId` 时拒绝下载；
- 调用 `checkBeforeDownload(fileId, storedHash?)`；
- 下载前检查失败时按 fail-closed 返回失败。

但我这次核对到的文本任务附件预览链路，图片预览仍是直接 `window.open(url, '_blank')`。我没有确认当前所有预览/下载入口都必经 `ensureAttachmentSafeForDownload()`。

所以对使用者的正确结论是：

1. **不要把“能点开附件”理解成“系统已经统一做过下载前复查”。**
2. **对来源不明的文件，先按普通文件安全规则处理。**
3. **如果你的实例强调强制下载前复查，请让维护者验证对应入口真的接上了这条 helper。**

### 签名 URL 不是永久地址

当前附件访问依赖时效性签名 URL：

- 当前配置有效期是 30 天；
- 运行中的会话会在链接接近过期时尝试刷新；
- 旧标签页、旧书签、旧导出里的直链都不应该被当成永久文件地址。

因此，不要把附件 URL 当成长期可分享的稳定链接，更不要把它抄到公开文档里当作永久地址。

## 软删除、后台清理与恢复

### 删除动作现在真正做了什么

当前“删除附件”的第一步不是硬删远端文件，而是：

1. 给附件写 `deletedAt`；
2. 把更新后的附件数组保存回任务；
3. 后续再由 cleanup 队列处理远端对象清理。

这意味着：

- 从任务里删除成功，代表“任务当前不再把它当活跃附件展示”；
- 不代表远端对象已经立刻消失；
- 也不代表 JSON 导出能替你保留原文件。

### 当前能不能承诺“删除后就地恢复”

不能。

源码里确实有 `restoreDeletedAttachment()` helper，但我这次没有核对到当前公开附件入口里的独立恢复按钮或撤销流。对使用者来说，正确做法是：

1. 删除重要附件前，先确认 ZIP 备份或原文件还在；
2. 删除后如果发现误删，不要假设当前页面一定能一键恢复；
3. 优先走 [项目、设置与回收站](09-project-settings-and-recovery.md) 中的项目级恢复、备份导入或实例维护者恢复流程。

### 什么时候才算“真正清理完”

对文件本体来说，真正清理完至少要满足：

1. 任务附件列表已经不再把它作为活跃附件使用；
2. cleanup outbox 已经把远端路径清掉；
3. 同步状态回到稳定；
4. 你不再需要从 ZIP 或原文件恢复它。

在这之前，都不要把删除动作理解成“不可逆销毁已经完成”。

## 跨设备与隐私边界

### 另一台设备什么时候才能看到附件

只有下面几件事都完成，另一台设备才有机会稳定访问：

1. 当前设备已经把待上传 Blob 真正发到远端 Storage；
2. 任务附件元数据已经写回并同步；
3. 另一台设备已登录正确账号并完成同步；
4. 访问链接未过期，且当前权限仍有效。

**本地 pending 附件不会自动跨设备迁移。**

### 当前实现对隐私做了哪些边界

这次核对到的边界包括：

- 附件路径按 `userId / projectId / taskId / attachmentId.ext` 命名；
- cleanup outbox 会校验路径 owner 是否匹配当前 `ownerUserId`；
- 本地 pending 上传和 cleanup 记录都按 owner scope 存储；
- 附件访问用的是私有 bucket 的时效性签名 URL，而不是永久公开 URL。

但你仍然不能把附件系统当成“可以随便放敏感数据”的免死金牌。不要上传密钥、生产导出、个人证件或不应放进个人工作区的材料。具体安全责任和共享边界，继续读 [安全与隐私](../03-data-sync-safety/04-security-and-privacy.md)。

## 备份、迁移与换设备

### 先分清哪种备份包含什么

| 备份形式 | 包含什么 | 不包含什么 |
| --- | --- | --- |
| JSON 导出 | 项目、任务、连接、附件元数据 | 原始附件文件 |
| 附件 ZIP 导出 | 原始附件内容 | 任务结构、任务关系、同步状态 |
| 本地增强备份 | 取决于你当前实例与浏览器权限 | 不能替代你对恢复结果的人工核对 |

### 换设备前的最小安全动作

换设备、换浏览器或准备清理当前浏览器数据前，至少做这几步：

1. 看同步状态条，确认没有长期停在 `X 待同步` 或 `连接中断`。
2. 如果仍有待同步，优先恢复网络并等待收敛。
3. 做一份 JSON 导出。
4. 做一份附件 ZIP 导出。
5. 重要文件保留原始副本，不要只信浏览器本地缓存。

完整恢复路径见 [备份与恢复](../03-data-sync-safety/03-backup-and-restore.md) 和 [离线优先模型](../03-data-sync-safety/01-offline-first-model.md)。

## 故障处置清单

### 1. 选中文件后立刻失败

先看错误类型：

- `文件过大`：先压缩、拆分或改用外部受控存储；
- `附件数量已达上限`：先整理当前任务附件；
- `文件类型验证失败`：不要改扩展名硬闯，先确认文件真实类型；
- `文件安全扫描未通过`：把它当成安全问题处理，不当成普通网络重试。

### 2. 离线或服务暂时不可用

看到离线横幅或 `连接中断` 时：

1. 不要清浏览器站点数据；
2. 不要切换到另一个账号指望它接管 pending 附件；
3. 继续在当前浏览器里工作，但把重要原件留在本地；
4. 网络恢复后，等同步状态自然收敛；
5. 长时间不收敛时，导出待同步数据并联系维护者。

### 3. 任务里有文件名，但别的设备打不开

按这个顺序排查：

1. 当前设备同步状态是否已清零；
2. 远端上传是否真的完成，而不是只有本地占位附件；
3. 另一台设备是否登录同一账号、进入同一项目并完成同步；
4. 当前访问链接是否已经过期；
5. 这是不是一个需要下载前复查、但入口并未统一接线的旧链接。

### 4. 删除后想恢复

当前正确动作不是盲目重传，而是：

1. 先找原文件副本；
2. 再找附件 ZIP 或项目级恢复路径；
3. 没有验证到当前页面恢复按钮时，不要把“服务里有 restore helper”误解成“用户现在就能自己恢复”；
4. 必要时走维护者恢复。

## 常见问题

### 为什么任务里已经出现文件名，另一台设备还是没有？

因为当前实现会先保存本地 pending 附件，再异步做远端上传和任务元数据同步。文件名出现只能证明“当前设备已经记录了这次操作”，不能证明“跨设备已经可用”。

### 上传失败后为什么不建议马上刷新或清缓存？

因为未完成附件依赖当前浏览器里的 owner-scoped pending 记录。你一旦清站点数据、切无痕或换浏览器，原来的恢复上下文就不再可靠。

### 当前附件一定会统一显示扫描状态吗？

不能这样承诺。当前实现有完整扫描状态枚举和元数据，但我没有确认当前公开附件入口一定把每种状态做成固定 badge 或列表。

### 点击预览是不是就说明安全检查通过了？

不是。当前仓库里有下载前复查 helper，但我没有确认所有预览/下载入口都已经强制接上。至少这次核对到的图片预览链路是直接新标签页打开 URL。

### 删除附件是不是就已经彻底删掉远端文件了？

不是。当前删除是软删除优先；远端文件清理由独立 cleanup 队列异步收敛。
