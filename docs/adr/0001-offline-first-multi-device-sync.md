# 离线优先的多端同步采用持久化操作与冲突证据

Status: accepted

NanoFlow 必须在离线状态保持本地领域操作的即时可用，并在多个设备分别离线或联网时最终收敛，同时保持数据可导出、可恢复、可重放和可解释。现有系统已经包含离线快照、RetryQueue/ActionQueue、同步游标、服务端 decision、`baseUpdatedAt` 删除保护和 unknown-outcome 对账；因此新方案必须兼容这些语义，而不能把现有同步主链一次性替换掉。

## Decision

1. 本地领域操作先形成可继续工作的本地事实，再异步产生持久化出站操作；本地 UI 不等待远端确认。
2. 出站操作拥有稳定的所有者、安装来源和客户端操作身份，可幂等提交、重放和对账；未知结果先对账，不盲目重复提交。
3. 快照继续作为启动恢复和压缩历史的检查点；操作记录是多端离线收敛的主要语义载体。
4. 新操作使用字段级 LWW 和确定性排序；旧数据、旧客户端或服务端无法识别的操作继续兼容现有 `decision`、`baseUpdatedAt` 和删除保护流程。
5. 所有冲突都保留冲突证据。主状态可以只有一个，但输掉的版本、裁决依据和远端结果不能静默丢弃。
6. 删除通过删除墓碑传播；恢复是新的显式领域操作，不是把旧快照直接写回。
7. 现有快照、RetryQueue 和 ActionQueue 采用版本化、双读和惰性迁移；无法识别的数据进入可导出的隔离区，不做破坏性清理。
8. 实现按四层隔离：本地投影、outbox/replay、reconcile/conflict policy、现有同步主链 adapter。通过 feature flag 和场景矩阵验证后再逐步接入。

## Considered Options

- **只同步完整项目快照**：实现简单，但无法可靠表达多端并行字段修改、删除与恢复，也难以解释未知结果。
- **直接替换为纯客户端 LWW**：会破坏现有服务端 decision、`baseUpdatedAt` 删除保护和旧客户端兼容性。
- **遇到冲突就阻塞并要求人工选择**：能减少自动裁决风险，但违背离线无感使用目标。
- **一次性重写现有同步主链**：改动面和回滚成本过大，无法隔离验证数据安全保证。

## Consequences

该方案会增加操作元数据、迁移和冲突证据的维护成本，但能把“本地立即可用”和“远端最终确认”明确分开；在网络抖动、应用崩溃、双端同时编辑和未知结果场景下，可以保留原始事实并进行可解释收敛。旧同步路径在迁移完成前必须继续保留，不能因为新路径已有 focused tests 就宣称整个项目已完成。
